# WeCom self-built app setup

The QR-code-based WeCom bot channel uses the official long connection and only works inside the WeCom client. To chat from WeChat directly, use a self-built app: after members follow the enterprise's WeChat plugin in the WeCom admin console, they can message this app from WeChat.

This channel receives messages over HTTP callbacks, so it needs one extra step: making port 30987 reachable from the public internet. The guide below follows the actual setup order and focuses on the callback base URL.

## Before you start

- Admin access to the WeCom admin console, enough to create a self-built app.
- Note down the app's Corp ID, AgentId, and Secret; generate a Token and an EncodingAESKey under "Receive messages → API receive" for the app.
- A path for the public internet to reach local port 30987. WeCom's servers must be able to connect in — this is a hard requirement for an HTTP callback channel.

## Binding steps

1. Settings → IM bots → WeCom app → Add WeCom app. Fill in the six fields and click "Save and connect".
2. Once saved, the card shows the full callback URL.
3. Back in the WeCom console, paste the callback URL, Token, and EncodingAESKey into "Receive messages → API receive" and save. WeCom sends a verification request; once the plugin verifies the signature, binding is done.

The Token and EncodingAESKey must match what the plugin card has stored. Every press of "randomize" in the console requires syncing both sides; changing only one fails verification. Also copy the Corp ID carefully — it is longer than it looks.

## How to fill in the callback base URL

"Public callback base URL (optional)" decides the first half of the callback URL. Without it, the plugin can only show the path. Two options:

**IP plus port**, for example `http://43.198.123.45:30987`. No domain or certificate needed, and WeCom accepts plain http. The port must be reachable from the internet:

- When dsh runs directly on a cloud server, the plugin listens on `127.0.0.1` by default. Forward the port with iptables, socat, or similar, or set the plugin's `callbackListenHost` to `0.0.0.0` and restart.
- When dsh runs on a home or internal machine, use a tunnel such as frp to map a port on a public server back to local port 30987.

**A domain**, for example `https://im.example.com`. Makes sense when you already have a domain and certificate. Reverse-proxy the `/wecom-app-callback/` prefix to local port 30987 in nginx, openresty, or caddy; other paths are untouched:

```nginx
location /wecom-app-callback/ {
    proxy_pass http://127.0.0.1:30987;
    proxy_set_header Host $host;
}
```

Behind a reverse proxy, the callback URL on the plugin card shows the domain form, and you avoid keeping a port permanently open in the firewall.

Neither option is "better"; WeCom accepts both http and IP-style callback URLs. Changing the base URL changes the callback URL — update the WeCom console accordingly.

## API proxy (optional)

Calls to the WeCom API (access_token, sending messages, uploading files) go to `qyapi.weixin.qq.com` directly by default. Servers inside mainland China can usually leave this empty. From overseas the domain can be unreliable; set up a reverse proxy on a machine with stable access, point `https://api.example.com` at `https://qyapi.weixin.qq.com`, and fill that into "API proxy".

The egress IP of outbound requests must be in the "trusted IP" list of the WeCom app: use the server's public IP for direct connections, or the proxy server's IP when a proxy is configured. A mismatch returns errcode 60020.

## Streaming replies

Replies stream token by token in the WeCom client. The WeChat side has no streaming API, so the plugin falls back to sending the full message there. Nothing to configure.
Messages sent to the app from the WeChat plugin and from the WeCom client land in the same DSH session, so switching devices does not break context. However, your own sent messages are not mirrored on the other client (WeCom platform behavior): the WeCom client does not show what you typed from the WeChat plugin and vice versa, while the bot's replies appear on both.


## When verification fails

- The console reports "verification failed" or rejects the callback URL: in most cases the Token or EncodingAESKey differs from what the plugin card has stored. Open `base-url/wecom-app-callback/probe` in a browser — a 404 means the path is reachable; a connection error means the network path is not.
- Messages can be sent but no reply arrives: check that the trusted IP list covers the outbound IP.
- In the logs, errcode 60020 points to the trusted IP list, 41004 to a missing or incorrect Secret.

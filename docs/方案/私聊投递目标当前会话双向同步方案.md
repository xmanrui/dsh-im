# 私聊投递目标当前会话双向同步方案

日期：2026-09-05。状态：已实施并验收（尚未发布）。

实施与验收基线：

- dsh-im：`v4.10.0`，实施前 `main` 为 `610fed4`（每机器人模型设置）；本文件记录当前工作区中的未发布实现。
- DSH 既有兼容基线：`0.1.2-alpha.4`、`0.1.2-alpha.5`、`0.1.2-rc.1`。
- DSH 最新发布基线：`0.1.3-alpha.1`，官方提交 `d347e70`。已在真实 Web profile 上完成九渠道验收，package 兼容矩阵已加入该版本。

版本依据：[dsh-im v4.10.0](https://github.com/xmanrui/dsh-im/releases/tag/v4.10.0)、[DSH 0.1.3-alpha.1](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.3-alpha.1)、[DSH Session 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md)。

## 0. 难度与设计边界

实现难度为**中等**，不是九个渠道各做一遍的大工程。现有主动投递、私聊状态和统一 Adapter 已经覆盖大部分基础能力，真正需要谨慎处理的是：

1. 准确区分 DSH Web/CLI 输入与 dsh-im 的普通输入、`/steer` 输入，避免重复和回环。
2. 按新版 DSH 的 `turn + step` 语义合并最终助手文字，不能只取最后一条 `assistant/message`。
3. 把 `workspaces.json` 升到 v3 时保留已有的 `agentPresets`、`models`、`contextEnhancement`、`accessPolicies` 等字段，不能被旧的 v2 写入逻辑降级或覆盖。

实施前预计纯代码与自动测试约 4～6 人日；九渠道真实冒烟取决于账号和凭据，不计入这个估算。实际实现保持为一套共享协调器、一个 RPC 开关和现有九渠道发送路径，没有增加渠道专用同步层。

为避免过度设计，第一版限定为：当前本机 Host、九个聊天渠道、私聊、文字、当前 Session、在线尽力投递。显式配置 `harnessBaseUrl` 的远程 Harness 暂不支持会话同步；不建设远程事件中继、数据库、持久队列、Session ACL 或跨目标聊天室。

## 1. 最终结论

本功能直接扩展现有主动投递设置，不新建第二套目标、Session 绑定或渠道发送协议。

每个已保存的私聊投递目标增加一个默认关闭的“会话双向同步”开关。开启后，该目标自动跟随其私聊当前绑定的 Harness Session：

```text
IM 私聊消息
  → 现有 Bridge
  → 该私聊当前绑定的 Session

DSH 在该 Session 中产生的直接用户文字和最终助手文字
  → Host 会话同步协调器
  → 现有 DeliveryService
  → botId + targetId
  → 原私聊
```

用户不选择或保存 `sessionId`。`/session` 换绑后自动跟随新 Session；`/new` 清除绑定后进入等待，下一条私聊创建新 Session 后自动恢复。

完整定位关系是：

```text
同步配置 = botId + targetId + 私聊 conversationKey
当前 Session = state.sessionFor(conversationKey)
```

`conversationKey` 只在开启时由 Host 根据已持久化的私聊记录解析，客户端不能提交。配置中不保存 `sessionId`。

## 2. 用户体验

### 2.1 设置入口

沿用机器人设置页的“投递设置”。每个已保存目标在测试、编辑、删除操作之外增加一行：

```text
张三
targetId: zhangsan
类型：私聊

会话双向同步                         [关闭]
关闭时不发送 DSH 会话消息
```

开启成功后显示：

```text
会话双向同步                         [开启]
自动跟随该私聊的当前会话
```

当 `/new`、工作区切换等行为使私聊暂时没有当前 Session 时，开关仍保持开启：

```text
会话双向同步                         [开启]
等待该私聊建立新会话
```

不展示 Session 下拉框，不要求复制 Session ID，也不新增单独设置页。

### 2.2 开启条件

开启必须同时满足：

1. `botId + targetId` 已保存，不允许对未保存草稿开启。
2. 目标能与该机器人状态中一条已持久化的私聊 `conversationKey` 唯一匹配。
3. 该私聊当前已经绑定一个 Session。
4. 该渠道使用当前 Host 的内部 Harness 连接；配置了 `harnessBaseUrl` 时不可开启。

不满足时保持关闭并提示：

> 会话同步仅支持已经聊过、已建立当前会话且使用当前 Host Harness 的私聊目标。

群聊、频道、群内 Thread、Telegram Topic、飞书话题和无法确认属于私聊的手工目标不展示可用开关。不能仅根据 `kind` 或平台 ID 格式猜测私聊身份。Office 不是聊天私聊渠道，也不在本功能范围内。

### 2.3 开关语义

- 默认关闭；升级后所有既有目标仍为关闭。
- 开启只授权这个 `botId + targetId` 接收其当前 Session 的 DSH 侧文字。
- 关闭立即阻止尚未开始的后续同步投递，不影响普通主动投递。
- 多个已开启目标当前绑定同一 Session 时，分别向这些明确开启的目标发送。
- 这不是跨目标聊天桥：某个 IM 用户发来的消息不会转发给绑定同一 Session 的其他 IM 用户。

每个端点都是“IM 私聊 ↔ DSH Session”的可见性关系，不是“私聊 A ↔ 私聊 B”。

## 3. 同步内容与新版事件语义

第一版只同步文字：

| 输入或事件 | 处理 |
| --- | --- |
| DSH 直接用户输入产生的 `user/message` | 同步文字并加 `[来自 DSH]` 前缀 |
| dsh-im 普通提问或 `/steer` 产生的 `user/message` | 不同步，继续走原 Bridge 回复链 |
| DSH `assistant/message` | 按 Turn 内 step 顺序暂存定稿文字，Turn 成功后一次发送 |
| DSH `assistant/attempt` | 忽略；它表示没有形成表面消息的失败、重试或取消尝试 |
| `agent/assistant-stream` / dsh-im 合成的 `assistant/chunk` | 不订阅、不发送 |
| `surfaceOp` 不是 `append` 的消息 | 忽略，不同步压缩或替换结果 |
| 插件、Goal、Agent Team、工具、系统、审批和结构化问题 | 忽略 |
| 图片、文件及其他非文字块 | 忽略，不下载、不转码、不降级为路径文字 |
| 失败、取消、中断或超出 token 的 Turn | 不发送助手结果 |

新版 DSH 的字段位置按以下契约读取：

- `user/message` 文字来自 `event.data.content`。
- `assistant/message` 文字来自 `event.data.message.content`。
- `surfaceOp` 位于事件顶层，只接受 `event.surfaceOp === "append"`。
- `assistant/message` 是单个 step 的定稿，不是整个 Turn 的唯一最终消息。
- `assistant/message.stream` 仅用于 DSH 自身持久化和回放，本功能不解析。
- `turn/end.data.reason` 在新版是 `{ kind: "completed" }`；兼容旧事件时可同时接受字符串 `"completed"`，其他值一律视为未成功。

消息格式固定为纯文字：

```text
[来自 DSH]
请检查今天的构建结果。
```

```text
[DSH 助手]
构建已经完成，全部测试通过。
```

文字分段、平台长度限制和真实发送继续由各渠道现有 `sendProactiveText()` 处理。同步层不实现 Markdown、卡片或渠道专属格式。虽然新版 dsh-im 已支持通用文件与图片回传，本功能第一版仍不复用附件链路。

## 4. 领域关系与不变量

### 4.1 关系

```text
Bot 1 ── Delivery Target 1 ── Private Conversation A ──┐
Bot 1 ── Delivery Target 2 ── Private Conversation B ──┼─ Session X
Bot 2 ── Delivery Target 3 ── Private Conversation C ──┘
```

上述目标可以分别开启或关闭。只有明确开启且发送前仍绑定 Session X 的目标接收同步消息。

### 4.2 必须保持的不变量

- 投递地址仍由 `botId + targetId` 唯一确定；`sessionId` 永远不是投递地址。
- Session 归属始终来自渠道状态中的 `conversationKey → sessionId`，同步配置不复制这份绑定。
- 开启时只接受唯一匹配的私聊 `conversationKey`；零个或多个匹配都拒绝。
- 每次发送前重新确认目标仍开启，并且其私聊当前仍绑定本事件的 Session。
- 目标路由改变时不能把旧同步授权带给新接收人。
- 来源不明确时宁可不发：缺失 `rpcId` 的普通 `kind: "user"` 注入不当作 DSH 直接用户输入。
- dsh-im 来源判断必须在收到同步事件的回调中同步完成，再进入异步发送队列，避免来源登记先被清理。
- 一个目标发送失败不能影响 DSH Turn，也不能阻止其他目标发送。
- 同步出站不得再次作为渠道入站提交给 Harness；继续复用现有出站回声过滤。
- 协调器与现有 `HarnessReplyTracker` 必须共用同一套多 step 定稿聚合语义，不能维护两份略有差异的算法。

## 5. 私聊目标解析

### 5.1 复用现有候选解析

现有 `deliverySuggestionFromConversationKey()` 已能把持久化 `conversationKey` 转换为投递 `kind + route`。新增一个小型反向匹配函数，不另建九套路由表：

```js
resolvePrivateConversationKey(channel, sessions, target)
```

处理步骤：

1. 遍历 `sessions` 的 key。
2. 只保留该渠道明确属于私聊的 key 前缀。
3. 使用现有 `deliverySuggestionFromConversationKey()` 生成候选 `kind + route`。
4. 与目标规范化后的 `kind + route` 做精确比较，忽略 `targetId` 和 `name`。
5. 恰好一个匹配时返回其 `conversationKey`；否则返回不可开启。

九渠道私聊 key 沿用现状：

| 渠道 | 私聊 conversation key |
| --- | --- |
| 微信 | `p2p:<toUserId>` |
| 飞书 | `p2p:<openId>` |
| 钉钉 | `p2p:<userId>` |
| 企业微信 | `direct:<chatId>` |
| QQ | `c2c:<userOpenId>` |
| Slack | `direct:<channelId>` |
| Telegram | `direct:<chatId>` |
| Discord | `direct:<channelId>` |
| WhatsApp | `direct:<jid>` |

Telegram、Discord 和 Slack 等渠道的公共投递 `kind` 不能可靠区分私聊和群聊，因此必须按持久化 key 匹配，不能从 ID 正负、前缀或名称猜测。

### 5.2 为什么保存 conversationKey

开启时把已确认的私聊 `conversationKey` 保存到目标内部，而不是每次从 Session 列表重新推断。这样 `/new` 删除当前 Session 映射后，开关仍知道自己对应哪条私聊；下一次 `state.setSession(conversationKey, newSessionId)` 后即可自动恢复。

`conversationKey` 不是第二份 Session 绑定，也不是公共 API 参数，只是已授权投递目标和现有渠道状态之间的稳定连接点。

## 6. 持久化

继续使用各渠道现有 `workspaces.json`，把文档版本升级为 v3。已保存目标内部增加一个可选字段：

```json
{
  "version": 3,
  "workspaces": {
    "bot_a": "/Users/example/project"
  },
  "deliveryTargets": {
    "bot_a": {
      "zhangsan": {
        "name": "张三",
        "kind": "user",
        "route": {
          "openId": "ou_xxx"
        },
        "sessionSync": {
          "conversationKey": "p2p:ou_xxx"
        }
      }
    }
  }
}
```

实现要求：

- 在 Store 内引入 `CURRENT_DOCUMENT_VERSION = 3`，并保留 v2 作为既有 delivery/access 段的格式边界。
- 读取 v1/v2/v3。普通旧配置写入仍可保持 v1/v2；第一次开启同步时才升级为 v3，避免未使用本功能的用户失去旧版回退能力。一旦是 v3，后续任何写入都不得降回 v2。
- v1/v2 中缺少 `sessionSync` 时按关闭处理；不会自动为任何旧目标开启。
- v3 读写必须无损保留 `workspaces`、`agentPresets`、`models`、`contextEnhancement`、`deliveryTargets`、`accessPolicies` 以及已有迁移语义。
- 持久化目标规范化器可以读取 `sessionSync`；公开 `target.create` 和 `target.update` 的严格请求白名单仍拒绝客户端提交该字段。
- 缺少 `sessionSync` 即关闭，不保存重复的 `enabled: false`。
- 只修改名称时保留开关；修改 `kind` 或 `route` 时在同一次原子写入中删除 `sessionSync`。
- 删除目标自然删除同步配置；删除机器人沿用现有清理事务。
- 工作区切换和 `/new` 不删除开关，只让状态进入 `waiting`。
- Store 对外只返回 `syncEnabled` 或已装饰状态，不暴露内部 `conversationKey`。

不增加独立数据库、同步配置文件、消息历史、失败表或永久事件游标。

## 7. RPC 与设置页

### 7.1 最小 RPC 扩展

在现有 `/dsh-im-delivery` 通道增加一个端点：

```text
target.session-sync.set
```

请求严格为：

```json
{
  "botId": "bot_a",
  "targetId": "zhangsan",
  "enabled": true
}
```

成功返回：

```json
{
  "enabled": true,
  "state": "active"
}
```

关闭时不要求目标当前仍能解析私聊，只要目标存在即可清除配置。

现有 `target.list` 为每个目标附加只读状态：

```json
{
  "targetId": "zhangsan",
  "name": "张三",
  "kind": "user",
  "route": { "openId": "ou_xxx" },
  "sessionSync": {
    "enabled": true,
    "state": "active"
  }
}
```

状态只取以下值：

| 状态 | 含义 |
| --- | --- |
| `off` | 可用但未开启 |
| `active` | 已开启且私聊当前有 Session |
| `waiting` | 已开启，但当前尚无 Session |
| `unavailable` | 无法唯一匹配私聊、尚无可开启的当前 Session，或使用远程 Harness |

`target.create`、`target.update`、`target.delete`、`target.test`、`message.send`、HTTP 主动投递和 `ctx.dshIm.send()/listTargets()/listBots()` 保持原协议。开关只用于本地设置 RPC，不加入公开 HTTP 或 `ctx.dshIm` 服务。

### 7.2 设置页行为

- 目标列表加载时直接读取附加状态，不增加第二次列表请求。
- 开关保存期间禁用重复点击；失败时恢复旧状态并显示行内错误。
- 机器人离线时仍可开关；离线只影响真实发送。
- `unavailable` 时禁用开启，并显示第 2.2 节的说明。
- 编辑 `kind/route` 时提示“修改接收位置会关闭会话同步”。
- 删除确认提示同步设置也会一并删除。

## 8. 来源识别

不能依赖 `weixin-`、`telegram-` 等 RPC ID 前缀猜来源，也不能把所有 `source.kind === "user"` 都视为 DSH 人工输入。

### 8.1 独立的 Host 级输入来源登记

在 `harness-client.mjs` 中增加一个很小的 Host 级 `dshImInputRegistry`，使用与现有 interaction ownership 相同的 Host scope，但不复用审批/问题 ownership 的状态机：

- `HarnessClient.ask()` 在调用 `session.prompt` 前登记它的 `promptRpcId`。
- `steerActiveTurn()` 为每条 `/steer` 生成独立 `inputRpcId` 并登记。
- 旧 RPC steer 路径把该 ID 作为 RPC request ID 传给 `session.prompt`，由 DSH 回显到 `user/message.data.source.rpcId`。
- 当前 Host 的 `agent.inject()` steer 路径把同一 ID 放进 `steeringMessage().source.rpcId`；原 `promptRpcId` 仍只用于验证当前 Turn 的控制权。
- 注册项命中一次即消费；明确拒绝时立即删除；未形成 durable `user/message` 的项由有界、短时过期清理兜底。

`session/event` 回调一收到 `user/message`，先同步执行一次登记匹配并把结果附在内部队列项上，然后再做任何 `await`。这样不会因为 `ask()` 或 `/steer` 的清理先完成而把 IM 输入误认成 DSH 输入。

### 8.2 判定矩阵

| `user/message.data.source` | 判定 |
| --- | --- |
| `kind: "user"`、有非空 `rpcId`，且命中 dsh-im 登记 | dsh-im 输入，不同步 |
| `kind: "user"`、有非空 `rpcId`，且未命中登记 | DSH Web/CLI 直接用户输入，可同步 |
| `kind: "user"` 但没有有效 `rpcId` | 来源不明，忽略 |
| `kind: "team-message"` | Agent Team 内部消息，忽略 |
| Goal、plugin、tool、model 或未知 kind | 忽略 |

DSH 0.1.3 的 Agent Team 已提供独立的 `team-message` 来源与 sender 信息，本功能不把团队代理通信投递给私聊，也不额外实现团队消息桥。

## 9. 共享会话同步协调器

新增一个 Host 级共享模块：

```text
plugin-src/host/session-sync-coordinator.mjs
```

在九个聊天渠道 Adapter 注册完成后只启动一个实例，通过：

```js
ctx.on('session/event', handler, { global: true })
```

监听当前 Host 的 live durable Session 事件。DSH 0.1.3 的 `SessionHandle` 生命周期与 Session 格式 v2 不改变这个观察入口；协调器不自行打开、锁定、迁移或持久化 Session，也不订阅 `agent/assistant-stream`。

协调器只维护：

```text
turnStateBySession   每个 Session 当前 Turn 的来源、step 定稿文字和收件目标
sessionQueues        每个 Session 的短 Promise 队列
```

`turn/end`、新的 `turn/start` 或 Host 释放时清理对应状态。当前 Host 的 `session/event` 是实时单次通知，不做历史回放，因此不增加永久游标、重放扫描或额外去重层。

### 9.1 Turn 处理算法

```text
收到 turn/start
  1. 建立当前 Turn 状态，记录 turn；来源暂为 unknown

收到 step/start / step/end
  2. 维护当前 step，供没有 turn/step 字段的 user/message 归属当前边界

收到 append user/message
  3. 使用事件回调已完成的来源判定：
     - 首条有效 user-rpc 决定 Turn 来源是 dsh 或 im
     - IM、Goal、plugin、team-message 和未知来源不发送
     - dsh Turn 中后续未登记的 user-rpc 文字也可发送
     - dsh-im 登记的 /steer 始终跳过
  4. 对 DSH 文字查找当前绑定此 sessionId 的全部已开启目标
  5. 并行发送“[来自 DSH] ...”
  6. 记录成功目标；同一 Turn 有多条 DSH 用户文字时，只保留每条都成功收到的目标

收到 append assistant/message
  7. 仅处理 DSH 来源 Turn、相同 turn、interrupted !== true 的定稿
  8. 按 step 保存或替换文字，不发送 stream/chunk

收到 turn/end
  9. 把 reason 规范化为字符串或 reason.kind，仅 completed 继续
 10. 按 step 升序，用空行拼接全部定稿文字
 11. 对步骤 6 的目标逐个重新校验：
     - 目标仍存在并开启
     - conversationKey 当前仍绑定本 sessionId
 12. 并行发送“[DSH 助手] ...”，然后清理 Turn
```

首条有效输入来自 dsh-im 时，整个 Turn 都不由协调器发送助手结果，避免和现有 Bridge 的最终回复重复。开启发生在 Turn 中途时不补发半轮内容；关闭或换绑发生在 Turn 中途时不发送最终回复。

### 9.2 多 step 助手正文

当前 dsh-im `main` 已修复九渠道多 step 回复：流式草稿按 step 累积，同 step 的 durable `assistant/message` 替换草稿，最终按 step 顺序拼接。

本功能不复制另一套状态机。把 `HarnessReplyTracker` 中“按 step 替换并聚合定稿”的部分提取为一个可复用的小型纯 helper：

- 协调器只喂 `assistant/message` 定稿，不喂 chunk。
- 有合法 `step` 时按 step 升序聚合。
- 兼容旧 fixture 或旧 Host 缺少 step 时，退化为“最新 canonical message”，不与有 step 的路径混合猜测。
- `assistant/attempt` 和 `assistant/message.stream` 不进入 helper。

### 9.3 顺序与失败隔离

- 同一 Session 的事件进入一条 Promise 队列，保证用户文字先于最终回复；不同 Session 可并行。
- 同一事件的多个目标使用 `Promise.allSettled()`，一个失败不阻塞其他目标。
- 实际发送前由 DeliveryService 重新读取目标和当前 Session，不持有陈旧 route 快照。
- 发送失败只记录不含正文、原生 route 和 Session 历史的警告；不让 DSH Turn 失败。
- 沿用主动投递语义：不自动重试、不离线排队、不查询已读。

## 10. DeliveryService、Adapter 与本机边界

生产渠道 Adapter 增加三个内部方法；现有第三方或测试 Adapter 可以不实现，此时同步状态为 `unavailable`：

```js
setSessionSync(botId, targetId, enabled)
listSessionSyncTargets(sessionId)
sendSessionSyncText(botId, targetId, sessionId, text, options)
```

`BotWorkspaceStore` 增加两个对应方法：

```js
setDeliveryTargetSessionSync(botId, targetId, conversationKeyOrNull)
listSessionSyncTargets()
```

职责划分：

| 组件 | 新职责 |
| --- | --- |
| `BotWorkspaceStore` | 保存或清除目标的 `sessionSync.conversationKey` |
| Delivery Adapter | 解析私聊 key、读取当前 Session，并调用现有主动发送 Controller |
| `DeliveryService` | 选择 Adapter、汇总目标、保存前和发送前复验 |
| 会话同步协调器 | 识别 DSH Turn、聚合可见文字、控制顺序与失败隔离 |
| 渠道 Controller/Runtime | 不新增同步接口，继续发送主动文字 |

同步发送仍走：

```text
sendSessionSyncText()
  → 复验开关和当前 Session
  → coreController.sendProactiveText()
```

Host 创建 DeliveryService 时，根据每个渠道是否显式设置 `harnessBaseUrl` 建立一个只读可用性表。远程渠道的 `target.list` 返回 `unavailable`，开启请求返回稳定错误；不改九个渠道的事件连接，也不为远程 URL 建立 mux。该判断只需放在 Host/DeliveryService，共享生产 Adapter 不需要渠道专属分支。

## 11. 状态变化和竞态

| 场景 | 结果 |
| --- | --- |
| 开启时目标尚未聊过或没有当前 Session | 拒绝开启 |
| 渠道配置了 `harnessBaseUrl` | 显示 `unavailable`，首期不启用 |
| 开启后执行 `/session` | 下一条 DSH Turn 自动跟随新 Session |
| 开启后执行 `/new` | 状态变为 `waiting`；新 Session 建立后恢复 |
| 开启后切换 Workspace | 原映射清除并等待；新会话建立后恢复 |
| 多个目标或机器人绑定同一 Session | 只向分别开启的目标发送 |
| Turn 运行中开启 | 不接收这半个 Turn，从下一条 DSH 用户输入开始 |
| Turn 运行中关闭、换绑或删除 | 不再发送该 Turn 的后续消息或最终回复 |
| 只修改目标名称 | 保持开启 |
| 修改目标 kind 或 route | 原子关闭，用户需重新开启 |
| 机器人离线 | 本次发送失败；不重试、不积压 |
| Host 重启 | 不补发历史，只处理重启后的 live 事件 |
| DSH `/pause goal`、取消或崩溃修复结束 Turn | 非 completed，不发送助手结果 |
| DSH 多 step 或工具循环 | 只在 completed 后发送按 step 聚合的最终文字 |

## 12. 安全边界

- 默认关闭，既有用户升级后不会突然收到 DSH 内容。
- 只允许已持久化且唯一匹配的私聊，不支持群聊和无法证明来源的手工地址。
- 设置页明确提示：开启后，当前 DSH Session 的直接用户文字和助手最终文字会发送给该私聊用户。
- 多个目标共享 Session 时，各目标必须分别开启，不能因执行 `/session` 自动订阅。
- 来源校验失败时关闭式处理，不同步缺失身份的 `kind: "user"` 注入。
- 不同步工具参数、工具结果、推理、系统提示、插件/Goal/Agent Team 注入、审批内容、文件路径或附件。
- 日志不记录同步正文、平台原生 route 或 Session 历史。
- 公网 HTTP 主动投递接口和 `ctx.dshIm` 不增加开关权限；配置仍受现有 Connection RPC authority 限制。

用户主动为多个私聊目标开启同一 Session，同样等于授权这些目标接收该 Session 的 DSH 侧可见文字。设置页应明确警告，但本期不建设成员、角色或 Session ACL。

## 13. 明确不做

为保持实现简单，本期不做：

- 不支持显式 `harnessBaseUrl` 的远程 Session 事件同步。
- 不新增 Session 选择器、主目标或“最后发言人”推断。
- 不把 IM A 的消息转发给 IM B。
- 不同步群聊、频道、Topic、Thread 或 Office 任务。
- 不同步流式进度、Reaction、输入状态、卡片、图片、文件和 Artifact。
- 不同步审批、结构化问题、Goal 或 Agent Team 消息。
- 不解析 `assistant/message.stream`，不发送 `assistant/attempt`。
- 不接管 DSH `SessionHandle`、Session 锁、格式迁移或历史回放。
- 不补发开启前或 Host 停机期间的历史。
- 不实现数据库、持久消息队列、自动重试、回执、已读和投递历史。
- 不修改 DSH 事件协议、公开 HTTP `message.send` 或 `ctx.dshIm` 协议。

### 15.2 真实冒烟

1. 保存投递目标并完成现有测试投递。

5. 执行 `/new` 后确认进入等待；再发一条 IM 消息建立新 Session，确认自动恢复。

# Issue #215：QQ 状态损坏恢复与实测记录

问题：[Issue #215](https://github.com/xmanrui/dsh-im/issues/215)。

实测日期：2026-09-16，Asia/Taipei，主要收发验证在 00:08–00:16 完成。

## 修复结果

QQ 的状态文件出现全零、空文件或截断 JSON 时，现在先保存原始字节备份，再通过已有临时文件与 rename 写入空状态。成功完成加载后才缓存 Store、启动连接。

- 读取、解析、备份和写入分别处理；只有 JSON 解析的 SyntaxError 触发恢复。
- 不存在的状态文件继续自动创建。
- 备份使用时间戳与 UUID 命名，使用 `wx` 独占创建和 `0600` 权限。
- 备份失败时保留原文件并停止恢复。重建写入失败时，原文件与已完成的备份都保留，下一轮可重试。
- 使用 `state-read-failed`、`state-backup-failed`、`state-write-failed` 区分故障。启动、手动绑定、扫码绑定、手动重连都保留具体错误。
- 状态中的 `health.summary` 与具体错误一致；QQ 管理 RPC 的异常出口也保留状态错误码。设置页沿用既有错误展示，中英文提示均已补齐。
- Store 使用生产装配传入的 QQ logger，恢复成功发出 `state-recovered` 警告，包含原文件、备份位置和状态重置影响。

实现由现有 QQ Store、Controller、生产装配、RPC 和一个小的错误映射模块组成，沿用原来的重试、缓存和保存机制。依赖和状态文件版本保持兼容。本次交付对应方案中的首个独立 QQ 修复，其他渠道的恢复策略作为后续工作。

## 恢复边界

重建会丢失损坏文件中的会话映射、消息去重记录和待补发记录；下一条消息可能创建新会话，重新投递的消息可能被再次处理。损坏备份用于排查，不承诺能恢复其中的数据。

本修复解决损坏文件阻止启动的问题，没有确定现场文件变成全零的起因，也不声称现有临时写入机制能保证断电后的磁盘持久性。机器人配置、凭据与工作区配置不使用状态清空恢复策略。

## 本机 QQ 实测

环境：macOS，原版 DSH `0.1.5-rc.2`，Web profile，监听 `127.0.0.1:3080`；QQ 客户端中已登录的真实机器人 **winBot**。插件使用当前工作区构建，通过本机已有链接加载。

测试前备份插件构建、profile patch、QQ 配置、工作区设置和完整会话状态，并确认待补发队列为空。通过临时 HMR 模块重载插件，Host 一直保持 PID `35576` 和原启动时间。DSH 源码工作区保持干净。

### 全零文件恢复

将真实机器人 `state.json` 替换为 449 字节全零内容，重载插件。新 Store 自动生成损坏备份、创建合法空状态并建立 QQ 连接。备份内容与注入字节完全一致。

从 QQ 私聊发送限定回复、禁止调用工具和修改文件的测试消息，winBot 独立回复：

```text
ISSUE215_QQ_RECOVERY_OK_20260916
```

QQ 可访问性文本和截图均显示独立回复；管理状态为 connected/healthy，收到与回复计数均为 1。

### 恢复写入失败与自动重试

在临时写入路径 `state.json.tmp` 创建空目录，再注入全零状态并重载。这使真实文件写入失败：

- QQ 状态报告 `state-write-failed`，提示检查磁盘空间与目录写权限。
- 手动重连 RPC 同样返回 `state-write-failed`。
- 原文件仍是完整的 449 字节全零内容，损坏备份保留。
- 只删除测试创建的空目录，既有连接监督器随后自行重试、重建状态并重连；这一步没有重启或重载插件。

QQ 私聊再次获得独立回复，收发计数均为 1：

```text
ISSUE215_QQ_RETRY_OK_20260916
```

### 截断 JSON 与日志接入

再次使用 `{"sessions":` 截断内容验证，自动备份和恢复成功。

本机原有 stdout 日志未输出 QQ 的 warn 记录。核对宿主 Cordis 实现后，通过临时的、仅接收 `dsh-im:qq` 且级别为 2 的日志 exporter，实际捕获到生产 Store 发出的 `state-recovered` 警告。该接收器使用宿主现有 `ctx.logger.exporter()`，测试后移除。

这证明日志已接入宿主 logger。警告是否出现在用户的某个日志文件，仍由宿主 exporter 和级别配置决定；本次没有改变宿主默认日志设置。持续失败时，用户可直接从 QQ 状态及设置页读取具体错误，不依赖找到日志文件。

一次只读状态采样恰好发生在 HMR 卸载路由期间，收到 HTTP 404。对仍在运行的同一 Host 重新采样后成功，没有将该瞬时结果当作状态恢复失败或重启服务。

### 恢复原会话后复验

恢复测试前完整状态的会话映射、归档设置和待补发字段；去重记录保留原有 181 条并合并本次测试消息。恢复原 profile patch，移除临时 HMR 和日志接收器。

原会话中再次完成真实私聊收发，winBot 独立回复：

```text
ISSUE215_QQ_RESTORED_OK_20260916
```

QQ 可访问性文本和截图确认回复，输入框无遗留草稿；最终状态 connected/healthy，收发计数均为 1。

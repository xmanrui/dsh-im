## 修复内容

- 保留 PR174 的 `createAndDeliver`，创建和投放时携带初始内容。
- 共享模板继续使用 `msgContent` 展示正文，`staticMsgContent` 留空，`sys_full_json_obj.order` 固定为 `["msgContent"]`。

字段和完成顺序与使用同一模板的 [DingTalk OpenClaw Connector 实现](https://github.com/DingTalk-Real-AI/dingtalk-openclaw-connector/blob/cb302aba1c464ef572d958800b83f2f8bd2a893d/src/services/messaging/card.ts) 一致。

## 实机结果

| 场景 | 方法 | 结果 |
| --- | --- | --- |
| 正常卡片 | 从 macOS 钉钉客户端发送测试提示，经本地运行中的 Harness 与模型自动回复 | 客户端显示完成状态，卡片完整显示三行正文；本地出站记录逐字匹配 |
| 最终流式帧失败 | 独立测试 Bridge 对最终流式请求注入一次 HTTP 500，其余卡片与文字请求访问真实钉钉 API | 文字发送一次，完整答案在客户端可见，成功计数为 1 |
| 完成状态更新失败 | 独立测试 Bridge 在流式完成成功后，对实例完成状态请求注入一次 HTTP 500 | 同样成功实发一次完整文字答案，未误报卡片完成 |

最终正常测试的标记为 `PR174_LIVE_OK_20260909_C`，正文包含 `计算结果：9 + 6 = 15` 和 `卡片完整显示，验收完成。`。这一轮卡片完全由运行中的插件生成，没有手工调用 API 补写。此前排查轮次中手工更新过的卡片不作为这一轮通过的证据。

两轮故障注入使用固定答案的测试 Harness、独立内存状态与真实 Bridge。文字由 `sendRobotText` 发送给同一个测试收件人，不是通过会话 webhook；故障没有注入运行中的 Host，也没有写入产品代码。两种故障的测试标记分别以 `PR174_LIVE_FALLBACK_OK_20260909_final-frame` 和 `PR174_LIVE_FALLBACK_OK_20260909_finished-state` 开头。

本记录仅覆盖上述一台机器人私聊，不将其外推为群聊、其他机器人或移动端验收。测试没有修改机器人凭据、模型选择或工作区设置。

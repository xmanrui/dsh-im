# Issue #232：飞书面板补齐命令的最小方案

日期：2026-09-21。状态：已实施；已完成的验证见第 7 节，按用户要求结束后续测试。

关联反馈：[Issue #232](https://github.com/xmanrui/dsh-im/issues/232)。

**直接在现有 SLASH_COMMAND_MANIFEST 中补上 17 个已经支持的主命令，继续复用原注册流程。核心生产代码只改一个文件。**

## 1. 用户可见的结果

当前飞书面板注册 14 个命令。补齐后共 31 个条目，用户可以从面板发现并选用现有的模型、Preset、任务控制、历史等功能。

需要参数的命令仍由用户填写参数，例如 `/session <ID>`、`/steer <补充指令>`。面板只注册命令名称；参数提示、实际执行和权限判断使用现有处理器。

## 2. 本次新增的 17 个命令

| 功能 | 新增面板项 |
| --- | --- |
| 历史 | `/history` |
| 工作区与会话 | `/workspace`、`/conv`、`/session` |
| 模型与推理 | `/models`、`/model`、`/reasoninglist`、`/reasoning` |
| Agent Preset | `/presetlist`、`/preset` |
| 任务控制 | `/stop`、`/steer` |
| 批量输入 | `/batch`、`/send`、`/cancel` |
| 版本与权限修复 | `/version`、`/repair` |

其中 16 项来自当前公共命令目录中已被飞书处理器支持、但面板未列出的主命令，另一项是飞书专用的 `repair`。已经核对飞书 bridge 与其使用的共享处理器入口。

原有 14 项全部保留：`menu`、`new`、`help`、`status`、`compact`、`sessionlist`、`workspacelist`、`workspaces`、`wsl`、`ws`、`watch`、`unwatch`、`watchlist`、`archived`。

本次新增主命令即可；`/conversation`、`/thread`、`/sessions`、`/reasonings`、`/presets`、`/m` 等别名继续由原处理器支持，不额外为同一功能增加重复面板项。原来已展示的别名保留。

## 3. 实现方式

修改 `src/channels/feishu/slash-command-registry.mjs` 内已有的 `SLASH_COMMAND_MANIFEST` 数组，追加上述条目：

- 沿用 `{ command, icon, default, en_us }` 结构。
- `command` 只写名称，不包含斜杠、空格或参数占位符。
- 中英文说明沿用现有帮助或公共目录的含义；每条写简短的用途说明。
- `history`、`batch`、`send`、`cancel`、`repair` 的说明标注仅私聊。
- 优先复用现有图标，其他项使用已有默认图标。
- 保留原有条目的名称、说明和相对顺序，新增条目按上表的功能顺序追加。

原 `registerSlashCommands()` 已经能够完成所需行为：

1. 查询远端已注册命令。
2. 跳过已经存在的命令。
3. 创建新增清单中尚未注册的命令。
4. 沿用现有权限错误、重复创建、超时和取消处理。

因此不需要修改注册算法、Runtime、StateStore、Controller、命令执行器或配置接口，也不增加新依赖。

此次只补齐面板，继续使用现有帮助文本。公共命令目录用于核对遗漏和测试覆盖，不同时实施目录统一或帮助卡片重构。这是明确的范围取舍：先以最小变更修复当前缺项。

本次不删除或更新远端已有条目；不涉及 `/mnemon`、命令归属、迁移、接管、清理脚本或新的管理界面。

## 5. 验证

复用现有测试及 fake HTTP，补充以下必要检查：

1. **覆盖缺项**：用当前已确认适用于飞书的公共主命令进行覆盖核对，并覆盖飞书专用 `repair`；保留原有 14 项，名称无重复，新增条目包含中英文说明。
2. **升级场景**：模拟服务端已存在原 14 项及一个外部条目，运行真实默认 manifest，只创建缺少的 17 项。
3. **重复启动**：让同一个 fake 服务端保存上一次的创建结果，再次注册时没有新增请求。
4. **外部条目保留**：注册过程不发送 DELETE 或 PATCH，外部条目不受影响。
5. **原机制回归**：继续运行已有缺少权限、重复创建和 Runtime 启停相关测试。

先执行斜杠命令注册和飞书 Runtime 的定向测试，再按仓库现有 `npm run check` 完成构建、测试和打包检查。工作区已有其他任务改动，验证记录需区分相关性。

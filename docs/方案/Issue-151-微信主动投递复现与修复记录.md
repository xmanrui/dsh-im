# Issue #151：微信主动投递复现与修复记录

测试日期：2026-09-05 至 2026-09-06（Asia/Taipei）。下表统一使用 UTC 时间。

## 结论

[Issue #151](https://github.com/xmanrui/dsh-im/issues/151) 的拒发现象已在真实微信账号上复现。**只补 `context_token` 不能彻底解决本次问题**：新收到的上下文仍然会被 iLink 以 `ret=-2 / prepare failed` 拒绝；同一时间 `getconfig` 正常，重启 Host 也不能恢复。接收者再发一条消息后，主动投递恢复。

本次完成的客户端修复是上下文保存与复用，以及主动投递失败的可见性。没有绕过或解除服务端的会话时效、消息额度限制，不能据此认定 #151 已彻底解决。

## 环境与范围

- 初次复现时本机插件为 4.11.0；修复基于 4.12.0、提交 `86ae0da`。
- DSH Host：`0.1.3-alpha.1`；iLink 协议：`2.4.6`。
- 一个已绑定微信机器人及其所有者的已保存私聊目标。
- 实际调用本机 `/api/dsh-im/delivery/messages` 和该账号配置的 iLink `sendmessage`、`getconfig`。
- 接收端为本机微信的 DeepSeek Harness 会话，已目视核对测试消息和 `pong`。
- 不另开 `getUpdates` 消费者，不重新扫码，不通过清空游标获取历史上下文。

第二轮从 `/ping` 开始，成功的机器人消息共 10 条：1 条 `pong`、1 条带上下文的 HTTP 消息、8 条不带上下文的直接发送。随后，两种发送方式都失败。

这支持本次失败与服务端消息额度有关；上下文当时只有几分钟，不能解释成“遗漏字段”或仅仅是长时间过期。**10 条是本次观测值，没有作为固定阈值写进代码。** 上游也有类似报告，但不是稳定接口合同：[Tencent/openclaw-weixin #202](https://github.com/Tencent/openclaw-weixin/issues/202)。`ret=-2` 也不能普遍等同于额度耗尽或上下文过期。

## 客户端修改

1. 通过访问检查的入站消息更新对应用户的上下文；拒绝重复或更旧的序列更新，使用精确整数处理大序列号。
2. 上下文按机器人账号、登录凭据和用户隔离，持久写入账号状态。Host 重启、切换 Harness 会话或工作区不会丢失；更换登录凭据时清除。普通状态快照不包含上下文。
3. 主动投递、连接测试和延迟任务结果复用对应用户上下文，不要求调用方提供 `context_token`。
4. 主动投递失败写入账号的 `lastMessageError`，保留平台错误码、上下文是否存在、消息长度等脱敏诊断；不包含登录凭据、上下文值、收件人或消息正文。
5. 正常长轮询不会覆盖发送失败。平台明确拒发与网络结果不确定分别展示，后续成功投递会清除发送错误。HTTP/RPC 保持原有错误合同，不自动重试，也不因一次拒发中断正常轮询。

首次升级后，需要收到一次目标用户消息才能建立上下文缓存。此次真实测试已为本机测试账号建立缓存并验证恢复。

## 验证

- `npm run check`：构建成功，2,296 项测试全部通过，包产物校验通过。
- 回归覆盖：上下文跨重启恢复、登录轮换清理、用户隔离、乱序与重复保护、隐私快照、主动发送和延迟结果复用上下文。
- 拒发回归覆盖：一次调用不额外重试；健康轮询保持连接且保留失败；网络错误不会错误提示额度耗尽；成功后清除发送错误；日志不泄露测试私密值。
- 真实验证：补字段后仍拒发、重启后仍拒发、用户消息后恢复，以及本机状态中的诊断与恢复清除。

## 再次复现的方法

1. 在已绑定机器人的私聊里发送 `/ping`，等待 `pong`。
2. 对同一个已保存目标，通过主动投递 HTTP 接口发送短文字；间隔约 20 秒，最多尝试 15 次，第一次失败就停止。
3. 期间不要再向机器人发送用户消息，避免重新建立可发送状态。计数应包含 `pong` 等其他机器人回复。
4. 检查 HTTP 结果和账号的最近消息错误；即使连接健康，也可能看到 `provider=-2`。
5. 在失败后，接收者再发送 `/ping`，待回复后通过相同接口重试，核对是否恢复。

复现会向测试接收者实际发送消息。次数与等待时间只是本次测试边界，不代表平台保证。持续无人交互的可靠通知需要平台提供相应能力；反复发送机器人心跳不能被视为续期方案。

## 1. 采用的最小修法

**持久化事件由现有历史轮询处理；实时连接只补充推理片段。推理确认属于当前请求后才能展示。**

| 内容 | 沿用的来源和机制 |
| --- | --- |
| 任务开始及请求归属 | `session.history` 中的 `user/message.source.rpcId`，关联现有 `promptRpcId` 和 `targetTurn` |
| 工具调用、工具结果、助手定稿、任务结束 | 现有 `session.history` 轮询、排序和序号去重 |
| 实时推理片段 | 现有 mux、Host 广播、`reasoning-delta` 及片段去重 |
| 进度回调顺序 | 现有 `progressTail` |
| 飞书展示和最终答复 | 现有 `FeishuLiveCot`、bridge 的最后一步定稿文本及发送降级 |

这会让工具进展和结束状态等待下一次历史轮询，通常增加约 300 毫秒加请求耗时；确认归属后的推理仍通过 mux 实时展示。沿用当前轮询频率，不增加请求频率。

改动主要集中在 `src/channels/shared/harness-client.mjs`。不新增持久化存储、RPC、配置项、依赖或后台队列，不建立通用事件重放系统。

## 2. 修复断线后丢失最终答案

根因是同一个 tracker 同时接受 mux 和历史记录中的持久化事件。mux 先收到较新的 `step/end` 等事件后，会推进 `lastSeq`，使历史补回的最终答案被当作旧消息跳过。只保护 `turn/end` 无法覆盖这类情况。

具体修改：

1. 复用 `consumeAll(..., { fromMux })` 已有的来源标记，在处理事件的入口分流。
2. 对 mux 来源，只有直播模式需要的 `assistant/chunk`、`reasoning-delta` 进入推理处理；其他事件不进入回复 tracker，不修改 `lastSeq`、最终答案或 `finished`。包括实时 `text-delta`，也不让它推进回复序号。
3. 历史来源继续使用现有排序、文本累积、工具映射及任务结束逻辑。最终答案和结束判断统一以历史记录为准。
4. 删除“仅对跨序号的 mux `turn/end` 延后结束”的特殊分支，它不再需要。

这里的分流仅作用于回复 tracker。`watchInteractions` 对提问、审批、停止控制和 ownership 的处理继续保留，不能把这些事件从全局 mux 中过滤掉。其他调用方的 `watchHarnessEvents` 也保持原有行为。

复用现有 `sleep(300)`、`session.history`、`progressTail`、超时与运行状态探测。无需为重连额外启动轮询器，也无需分别维护“已看见最大序号”和“连续序号”等多套游标。

## 3. 修复上一轮推理混入当前请求

根因是尚未匹配当前请求时，就根据推理帧自带的 turn 直接展示。会话中上一轮任务尚在执行、新请求正在排队时，这会把上一轮内容送入新请求的飞书消息。

具体修改：

1. 删除绑定前直接 `pushUpdate({ type: 'reasoning', ... })` 的行为。
2. 在每次 `ask()` 自己的 `HarnessReplyTracker` 内增加一个小的待确认片段缓存，复用现有事件的 `turn` 和 `seq`。缓存仅保存尚未关联请求的推理片段，不保存其他事件。
3. 下一次历史轮询时，将缓存片段与历史事件合在一起，复用现有按 `seq` 排序的处理方式。历史中的 `user/message.source.rpcId` 匹配当前 `promptRpcId` 后，才能确定目标 turn。
4. 关联成功时先输出 `turn-start`，再放行属于目标 turn 的待确认推理；其他 turn 的候选片段丢弃。排序中已经走到、但早于绑定消息的推理暂存到绑定点再释放；之后的片段按原有事件顺序处理，不能把后续步骤的全部推理一口气提前到任务开头。
5. 关联成功后的 mux 推理，只有 `event.data.turn === targetTurn` 才能输出；任务结束后忽略迟到片段。mux 推理不推进历史处理序号，整数或小数序号都遵守这一点。
6. 复用现有片段序号去重，使同一片段经过 mux、缓存和历史出现时只展示一次。缓存中的“已暂存”和“已输出”要区分：不能因为暂存时记为已处理，导致释放时又把本轮推理跳过。

缓存用一个 request-scoped `Map` 即可，不引入新的队列类或共享会话服务。设置简单固定上限，例如最多 256 帧、合计 64 Ki 字符；超限淘汰最早候选片段，避免请求长时间排队积累上一轮推理。关联成功后清掉其他轮次内容，结束或取消时随当前请求释放；极端超限只允许损失部分过程展示，不能影响答案恢复。

不需要修改飞书消息协议或另建任务 ID 映射。tracker 保证先输出正确的 `turn-start`，已有 `FeishuLiveCot` 就会沿用本轮编号。保留 bridge 已修好的“最后一步定稿文本作为最终答复”，以及长工具参数的截断逻辑。

# PR #255：飞书多表格卡片修复方案

方案日期：2026-09-23；实施与验收：2026-09-23 至 2026-09-24（Asia/Taipei）。状态：已按要求先合并，再完成修复及本机飞书验收。

依据：[PR #255](https://github.com/xmanrui/dsh-im/pull/255)，审阅提交 `3623ef345e0e871c027e485cd128cda3780a91f3`；核对时 main 为 `c0df316e0fc7beb4d45755c78957b79b4c3b9642`。实施时已重新核对，实际合并基线为 `6074db0`。

采用局部修复：在现有卡片工具文件中统一表格识别与拆分，在 bridge 中统一当前这一组卡片的同步。实现继续使用现有卡片结构、发送队列和失败补发机制。

**1. 目标与已确认的问题**

本次处理分步流式卡片及复用同一渲染流程的会话镜像。表格数量上限沿用该路径实测的 5 个，不推广到所有飞书接口。

| 已复现的问题 | 修复后的行为 |
| --- | --- |
| 两段各含 3 个表格的内容进入一个 notes 面板，仍被当成两行而跳过拆分 | 按实际表格数量拆分，每张卡不超过 5 个 |
| 一条回答含 6 个表格，第三个表格在表头与分隔行之间被切断 | 每个表格的表头、分隔行和数据保留在同一 Markdown 元素内 |
| 表格省略外围竖线时，能被计数却不能被拆分 | 识别和拆分使用同一规则 |
| 审批换卡后更新新分片，覆盖审批前的卡片 | 仅更新当前这一组卡片，历史卡片保留原内容 |
| 折叠后分片数量不变但内容变化 | 对应卡片同步到新的内容分布 |

现有 500 字符思考摘要、面板字节预算及最终答案补发规则继续生效。内容完整性的要求是：拆卡不得额外丢失、重复或改写原流程决定保留的内容。

本次保证按表格数量拆分时不会截断表格；单个超大表格超过既有字节预算的处理属于原有长内容机制，不在本次扩展为新的分页功能。

**2. 表格拆分：一套识别规则，正文与面板共用**

落点：`src/channels/feishu/feishu-cards.mjs`。

先修表格识别，再修拆分，避免继续叠加不同正则。

- 增加一个文件内的表格扫描函数，返回表格起始位置。`countMarkdownTables()` 取扫描结果的数量，正文拆分使用同一组位置。
- 只在“当前行为有效表头、下一行为对应的分隔行”时登记一个表格。识别后越过分隔行和表体，避免把分隔行或表体内的横线重复当成新表格。
- 兼容单列表格、对齐冒号、省略外围竖线、CRLF；单元格划分处理转义竖线和行内代码。跳过代码围栏及缩进代码中的示例，普通含竖线的文字不计数。
- 可参考仓库 QQ Markdown 工具已有的单元格与围栏识别写法，在飞书文件内实现所需的少量纯函数。飞书无需导入 QQ 投递模块，也无需新增 Markdown 解析依赖。

`splitBlockByTableLimit()` 保留现有入口，内部按以下顺序处理：

1. 正文 `block.text` 超过预算时，在下一组表格的表头起始位置切分。每段最多 5 个表格，保持文字顺序及表格内部换行。切点固定，不额外推测或重排说明文字的归属。
2. 面板 `block.lines` 的每个元素是一段完整 Markdown，可能有多个表格。先对每个元素调用同一个文本拆分函数，再按各片段的实际表格数顺序装入面板；判断条件为“已有数量 + 新片段数量 > 5”。
3. 删除 `lines.length <= maxTables`、`tableLines.length <= maxTables` 以及“含表格的 line 只加 1”的判断。
4. 返回新的展示块，不修改输入 `card.blocks`。保留 `kind` 等现有字段；一个面板拆成多个时，原 `omitted` 只附在第一片，后续为 0，避免重复计算已省略内容。
5. 面板展示计数沿用现有规则，不新增源步骤 ID 或跨面板计数模型。

外层 `splitStepStreamCardBlocks()` 继续负责顺序装卡，同时检查现有序列化字节预算与表格预算。正文和面板先规范成能满足表格上限的片段，再交给这个循环；分块本身不能作为跳过表格上限的理由。

统计结果应对应实际渲染的 Markdown：面板按 `lines.join('\n')` 的展示内容核对，不能仅假设数组长度等于表格数。测试需要检查卡片内各 Markdown 元素，防止相邻片段拼接后产生不同解释。

**3. 卡片同步：一个当前组起点，一个共同更新方法**

落点：`src/channels/feishu/bridge.mjs`。

保留 `card.cardIds` 作为本回合全部已发送卡片的清单，在现有 card 对象增加两个局部字段：

| 字段 | 用途 |
| --- | --- |
| `activeCardStart = 0` | 当前这一组卡片在 `cardIds` 中的起始位置 |
| `renderedCardContents = new Map()` | 当前组每张卡片最后一次成功写入的 JSON，用字符串比较跳过重复 PATCH |

不要把整个回合的 `cardIds[index]` 当成当前分片的 ID。所有映射统一基于 `cardIds.slice(activeCardStart)`。

提取一个 bridge 私有方法，例如 `#syncStepCardChunks(card, chunks, status)`，由运行中更新、最终收尾和审批换卡前的封存共同调用。该方法只做当前组的卡片同步：

1. 在开始网络请求前，固定本次目标 JSON 和答案版本。前面的卡片使用 `sealed`，最后一张使用调用方传入的 `running`、`completed`、`stopped` 或 `sealed`。
2. 对已有 ID，内容变化才调用现有 `#patchStepCard()`；内容相同直接跳过。分片数量相同也要逐张比较。
3. 分片增加时，按顺序调用现有 `#sendCard()`，成功取得 ID 后立即追加到 `cardIds`。保留现有话题回复与 open_id 投递参数。
4. 分片减少时，将实际内容右对齐到当前组已发送卡片，最后一张继续承载最新内容。多余的前置卡片更新为简短的“内容已合并至后续消息。”并封存，清除旧答案。提示通过现有翻译函数处理。
5. 每次成功写入后更新该 ID 的 JSON 缓存；全部目标写入成功后，才登记本次答案已送达、更新 `messageId` 及 `chunkCount`。
6. `messageId` 始终指向当前组最后一张卡；`chunkCount` 保持为当前组实际分配的卡片数。同步逻辑以当前组 ID 为准，不再依赖“分片只会增长”的条件分支。

分片减少时保留简短提示卡，是这里明确接受的简化取舍：不新增撤回消息请求及其失败处理，也不会留下重复的旧答案。后续分片再次增加时，可以直接复用这些位置。

运行中更新继续由现有 `renderChain` 串行执行。JSON 相同就跳过 PATCH，避免每次刷新都重写全部历史过程；无需新增调度器、并发更新或通用差异比较框架。

三个调用位置的处理如下：

| 入口 | 调整 |
| --- | --- |
| `#renderStepCardNow()` | 计算分片，调用共同方法，成功后更新现有镜像快照；失败沿用 broken 与补发处理 |
| `#finishStepCard()` | 等待已有渲染完成，写入最终答案，再用共同方法同步所有分片；仅全部必要写入成功才能确认最终答案已送达 |
| `#rotateStepCard()` | 等待渲染完成，以 sealed 同步当前组，然后设置 `activeCardStart = card.cardIds.length`、清空当前组 JSON 缓存，执行原有 blocks、答案区间和计时重置 |

审批前已封存卡片的 ID 继续保留在全回合清单中，但后续更新不得再写入这些 ID。审批或提问本身的发送、等待和权限处理沿用现有逻辑。

共同方法抛出的异常仍由原调用方处理；不另建重试机制。尤其保留现有 `answerVersion` / `renderedAnswerVersion` 的补发判定，记录的是本次成功写入快照对应的版本，不能在异步写入结束时误登记一个更新的内存版本。

**4. 镜像恢复与空内容兼容**

`#restoreMirrorCard()` 也要初始化上述字段。当前会话镜像流程没有审批换组，恢复时 `activeCardStart = 0`，继续使用保存的卡片 ID；JSON 缓存从空开始，首次同步允许重新 PATCH。

继续使用现有 `cardIds`、`blocks`、`lastContent` 等持久化字段，无需修改 StateStore 格式。新的起点和 JSON 缓存仅作为当前流程的内存状态。实现时保留“镜像全部卡片属于一个当前组”的现有约束，不将 IM 审批换组的全回合清单混入该恢复路径。

空内容沿用原行为：运行中没有可展示内容时不额外创建空卡；完成或停止需要状态卡时，按现有逻辑渲染。完成、停止、旋转和镜像恢复都复用同一份 ID 映射，不复制四套同步循环。

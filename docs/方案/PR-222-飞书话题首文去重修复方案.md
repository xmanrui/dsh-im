## 目标与取舍

同一个飞书话题在同一个 AI 会话里，成功使用过话题首文后，后续普通提问省略首文。命令、权限拒绝、读取失败以及新会话，都不能导致首文被提前省略。

采用一个 bridge 实例内的有界 Map，加上现有会话请求函数的一处可选扩展。复用当前的消息队列、会话绑定、工作区切换重试、引用读取和 prompt 构造。

去重是节省上下文的优化，处理结果不确定时允许下次重新注入。内存记录在机器人重启或淘汰后消失，恢复后的首次提问可能多带一次首文；这是本次接受的边界，不承诺跨重启或超时情况下严格只注入一次。

## 已有机制与落点

| 现有代码 | 本次复用方式 |
| --- | --- |
| `feishu/message-utils.mjs` 的 `extractInboundMessage()`、`replyTo.load()` | 保留无状态解析和延迟读取，重复解析不修改去重状态 |
| `FeishuHarnessBridge.#enqueueMessage()` | 同一 conversation key 已经串行处理普通消息，继续使用这条队列 |
| `shared/workspace-session.mjs` 的 `askInWorkspaceSession()` | 继续负责会话创建、存在性检查、绑定锁和工作区失效重试；从这里取得实际 sessionId |
| `shared/semantic/reply-reference.mjs` 的 `promptContentForInboundMessage()` | 继续处理引用降级、内容清洗、截断、附件摘要及引用块格式 |
| `enhanceContextContent()` 与已捕获的配置快照 | 继续使用原有来源信息和提示词增强，保持原有块顺序 |
| `askInWorkspaceSession()` 的返回值与 bridge 的 `markAskComplete()` | AI 请求成功后、飞书答案投递前记录去重状态；不把投递结果当成注入结果 |

## 实施步骤

### 1. 恢复无状态的消息解析

撤掉 PR 在 `message-utils.mjs` 新增的模块级 `topicAnchorOwners`、owner message ID 判断以及相关去重逻辑。保留原有 `parent_id` 优先、`root_id` 回退的引用解析。

PR 合并后撤回解析层的状态性去重，保留合并时 main 上的其他修复。PR 中把解析函数当作去重入口的两项测试改成 bridge 行为测试，并保留重复解析结果一致的检查。

### 2. 只识别明确的话题首文引用

在 bridge 内使用一个小的判断方法，满足以下条件才参与优化：

- `chat_type === 'group'`；
- 有非空 `thread_id` 和 `root_id`；
- 已解析的 `message.replyTo.messageId === root_id`。

无 `thread_id` 的群聊引用、私聊引用，以及引用话题中其他消息的情况，继续走现有路径。对于没有正文、图片或文件、只有引用的消息，也保留引用，避免优化后生成空请求。

### 3. 在实际会话确定后选择是否附带首文

给 `askInWorkspaceSession()` 增加一个可选参数 `prepareContent({ sessionId, content, text })`。它返回本次要提交的内容；未提供时仍直接使用 `content ?? text`。

调用位置在取得 `binding` 之后、执行 `binding.session.ask()` 之前，并且位于已有的工作区失效重试循环内。读取首文在绑定锁外完成，避免延长锁的占用。工作区切换触发重试时，使用新的 sessionId 重新判断，不能沿用旧会话的“省略首文”结果。

这个共享函数只传递实际 sessionId 和请求内容，不承担飞书话题规则。原有会话标题继续使用用户正文、图片默认提示和文件信息；来源增强快照、附件传递和超时补发沿用现有逻辑。

bridge 内将两处已有的 prompt 构造整理成一个小方法，复用 `promptContentForInboundMessage()` 和 `enhanceContextContent()`。仅话题首文路径通过 `prepareContent` 延迟决定引用是否加入，其余消息保持原路径。保留静态基础内容供原有标题逻辑使用，不通过解析生成后的 prompt 来识别或删除引用块。

### 4. 每个 bridge 只保存最近成功使用首文的记录

记录形式：

```text
Map<conversationKey, { sessionId, rootMessageId }>
```

一个 conversation key 只保留最近一条成功记录。只有实际 sessionId 和 rootMessageId 都匹配时才省略首文。每个机器人拥有独立的 bridge，自然隔离去重状态。

沿用已有 Map 容量限制的写法，最多保留 4,000 个会话键，新增键超过上限时删除最早的一条。淘汰只会让该话题下次多注入一次首文。

`/new`、切换会话、切换工作区，以及失效会话自动重建，继续使用现有 session 机制；实际 sessionId 改变后自然重新注入，不需要给这些命令分别添加清缓存代码。切换回更早的会话也可能重新注入一次，这是只保留最近记录的简化取舍。

### 5. 读取成功且 AI 请求完成后才写入记录

bridge 为当前话题引用的 `replyTo.load()` 加一层局部包装：直接调用原 loader，并记下是否取得可用正文或附件摘要且没有 `unavailableReason`。读取异常继续交给现有引用构造器降级，不改变公共返回格式。

每次 `prepareContent` 调用都重置本次读取结果，并绑定本次实际 sessionId。随后只有 `askInWorkspaceSession()` 正常返回、返回 sessionId 与本次准备结果匹配时，才写 Map。复用现有 `markAskComplete()` 调用位置，让纯文本、流式、分步直推和流式建立失败后的降级路径使用同一段提交逻辑。

- 命令和权限拒绝没有进入 AI 请求流程，不写记录。
- 首文读取失败或不可用，即使 AI 回答成功也不写记录，下次仍可读取。
- AI 请求失败、停止或超时，保守地不新增成功记录；不为本次优化增加补发状态同步。
- AI 请求已成功、飞书答案投递失败，仍保留成功记录，因为首文已经进入该会话。
- 不要在 `accept()`、`markSeen()`、会话创建成功、飞书消息投递成功或 `finally` 中提交这条记录。

简化后的流程：

```text
现有权限与命令分流 → 现有话题消息队列 → 解析当前消息
  → 现有机制确定实际 AI 会话
  → 比较该会话的首文记录，决定保留还是省略引用
  → 复用现有引用与 prompt 构造 → 提交 AI 请求
  → AI 请求成功且本次首文可用：记录 sessionId + rootMessageId
  → 沿用现有飞书答案投递
```

## 验证范围

优先把此前复现的 5 个用例放进 `test/channels/feishu/bridge.test.mjs`：首次 `/help`、首次 `/new`、已有会话后 `/new`、拒绝消息后正常提问、无 `thread_id` 的重复主动引用。

再用现有 fixture 覆盖以下行为，避免只测试 Map 实现本身：

| 场景 | 预期 |
| --- | --- |
| 同话题连续两次正常提问 | 首次带首文；第二次不带，也不再查询首文 |
| 同话题两条消息连续入队 | 首次完成后，第二条使用最新成功记录 |
| 首文首次读取失败，第二次读取成功 | 第二次仍能注入；失败不占用机会 |
| 首次 AI 请求失败，随后重新提问 | 首文仍会附带 |
| AI 成功但飞书投递失败 | 后续同会话提问不重复注入 |
| 绑定失效会话后自动新建，或工作区切换触发重试 | 按最终 sessionId 判断，新会话带首文 |
| 两个机器人实例处理同一话题 | 各自首次提问都带首文 |
| 两个话题、私聊重复引用、话题内引用其他消息 | 保持独立和原有引用行为 |
| 只有引用而没有正文/图片/文件 | 不产生空 prompt |
| 纯文本、流式、分步直推及建立流式失败后的降级 | 共用相同去重行为，单次请求不重复读取首文 |

在 `test/workspace.test.mjs` 补充可选内容准备函数的行为测试，并复用现有工作区切换测试验证重试时重新准备内容。未提供该参数的调用继续由原有测试覆盖。构造器共用方法若涉及会话标题，补验图片/文件首条消息的标题和来源增强块顺序。

实施后先运行上述相关测试，再运行仓库要求的 `npm run check`（构建、全量测试、包校验）。验证结果单独记录，区分自动化回归和真实飞书测试。

## 改动范围

核心实现落在 `src/channels/feishu/bridge.mjs` 和 `src/channels/shared/workspace-session.mjs`。如果在 PR 分支上修改，还需撤回 `message-utils.mjs` 的状态性去重。测试修改对应的 bridge、消息解析和 workspace 测试文件。

状态仅留在 bridge 内存中，现有 StateStore、磁盘格式、Host 注入协议及其他渠道调用方式沿用原样。成功记录依赖现有 AI 请求完成边界，允许不确定情况下重复一次，以保持方案小且容易验证。

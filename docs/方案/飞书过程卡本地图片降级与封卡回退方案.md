# 飞书过程卡：答案里本地图片降级 + 目标轮封卡失败回退

## 现象

会话 `session-d48a3338-ce31-419d-b3b5-1cb7903397cc` 里，目标第 1 轮（09:28 起，10:19:59 结束）在飞书留下了一张永远「运行中」的过程卡（工具摘要 146），10:20 又新开了第 2 轮的卡。第 1 轮的卡片没有变成「已完成」，本轮答案也没有出现在对话里。

## 根因

该轮最终答案里有一行 Markdown 图片，指向本机临时文件：

```
![标题画面](/tmp/host_13.png)
```

飞书卡片会把 Markdown 图片解析成 `img` 元素，要求 `img_key` 是已上传的图片 key；本地路径不是合法 key，于是整张卡更新被拒绝：

```
Request failed with status code 400
code: 230099
msg: Failed to create card content, ext=ErrCode: 200570;
     ErrMsg: card contains invalid image keys; ErrorValue: image key /tmp/host_13.png;
log_id: 20261102101959A39C4CC831A098245BC0
```

错误时间 10:19:59 正是该轮 `turn/end` 的时刻，与答案被写进卡片并触发渲染的时间一致。

链路：

1. `assistant/message` 收尾时，答案先作为草稿写进过程卡（`#streamStepCardAnswer` → `#writeStepCardAnswer`），包含上面那行图片；
2. 下一次渲染被飞书以 400 拒绝，`#renderStepCardNow` 把 `card.broken = true`，此后该卡的渲染全部跳过；
3. `turn/end` → `#sealGoalRound` → `#finishStepCard` 看到 `card.broken` 直接返回 `{ ok: false }`（此前是静默返回，没有日志）；
4. 目标续跑轮没有第二条投递路径，于是**状态停在「运行中」、本轮答案丢失**；卡片在封卡时已从 `#stepCards` 删除，所以第 2 轮顺理成章地新开了一张卡。

IM 发起的轮次同样会踩到渲染失败，但它们的调用方在封卡返回非 ok 时会回退到普通文本，因此只丢状态、不丢答案；目标轮此前两者都丢。

## 改动

1. **答案进卡前降级本地图片**（`src/channels/feishu/message-utils.mjs` → `stripLocalImageMarkdown`）：
   - 判据是「飞书能不能渲染这张图」：只有 `http(s)://` 地址与 `img_key`（`img_*`）保留，其余目标一律降级——绝对路径 `/x.png`、`./x.png`、`../x.png`、`~/x.png`、`file:///x.png`、`C:\x.png`、`C:/x.png`、`\\server\share\x.png`，以及 Agent 最常写的裸相对路径 `06-log/shot.png`、`data:` URI（实测裸相对路径同样会触发 `230099 / 200570`，卡片被打坏、答案降级成纯文本 Markdown 原文）；
   - 有 caption 就保留 caption（`![标题画面](/tmp/host_13.png)` → `标题画面`），没有 caption 就保留路径文本；
   - 远程 URL、既有 `img_key`、其余 Markdown 一律不动；
   - 调用点在 `#writeStepCardAnswer` 的最前面，因此流式草稿和封卡写入共用同一条路径，且分块大小按降级后的文本计算。
2. **封卡失败不再静默**（`src/channels/feishu/bridge.mjs`）：
   - `#finishStepCard` 在 `card.broken` 时写一条 warn，带上 `card.lastError`；
   - `#sealGoalRound` 检查返回值，封卡失败且本轮有答案时，用 `#send(chatId, answer, { replyTo })` 补发一条纯文本回复，保证结果送达；发送失败只记日志，不影响下一轮。

## 行为对照

| 场景 | 改动前 | 改动后 |
| --- | --- | --- |
| 答案含本地图片路径 | 卡片更新被拒 → 卡冻结在「运行中」，答案丢失 | 图片降级为 caption，卡片正常渲染并封成「已完成」 |
| 卡片因其它原因渲染失败（限流、内容异常） | 目标轮封卡静默失败，答案丢失 | 卡片仍冻结，但本轮答案以纯文本回复补投 |
| 远程图片 / Feishu `img_key` | 原样写入 | 原样写入（不受影响） |

## 取舍

- 不上传本地图片：需要 `im:resource` 权限、文件可读性与上传失败回退，收益（一次续跑截图）小于复杂度；先把「一张卡被图片拖死」的问题消掉。
- 图片信息不丢：caption 保留在正文里，读者看不到图但知道有个「标题画面」。
- 回退消息只在封卡失败时出现，正常路径不会多出一条重复消息。

## 验证

- `test/channels/feishu/card-markdown.test.mjs`：本地路径覆盖（Unix、相对路径、裸相对路径、`~`、`file:`、Windows 盘符与 UNC、`data:` URI）、caption 保留、无 caption 保留路径、尖括号/空格/title、远程 URL 与 `img_key` 不动、非字符串透传。
- `test/channels/feishu/goal-round.test.mjs` 新增两项：
  - 目标轮答案含 `![标题画面](/tmp/host_13.png)` → 卡片里有「标题画面」、没有 `![`、最终「已完成」，且没有额外的纯文本消息；
  - 卡片渲染被模拟拒绝 → 封卡失败后补发一条锚定话题的纯文本回复，内容为本轮答案。
- 反向验证：把 `src/channels/feishu/bridge.mjs` 暂存回旧版本，两项新集成测试均失败；改动后 10 项全过。
- 全量 `npm test`、`node scripts/verify-package.mjs` 通过。

## 已知边界

- 图片仍不渲染（只保留 caption）；需要真图时应由调用方先上传并用 `img_key` 引用。
- 已冻结的旧卡片不会自动补成「已完成」：封卡发生在 `turn/end`，此前的渲染失败无法追溯，只能保证答案通过回退消息送达。
- 该降级只作用于过程卡文本；普通文本消息不解析 Markdown 图片，无需处理。

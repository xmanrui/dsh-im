# Issue #234：图片输入修复与飞书实测

日期：2026-09-20。问题：[入站图片上限不可配置，超限后直接拒绝](https://github.com/xmanrui/dsh-im/issues/234)。

## 实现范围

统一处理飞书、微信、企业微信机器人、企业微信应用、钉钉、QQ、Slack、Telegram、Discord、WhatsApp 的现有图片入口。邮箱不在本次范围内；也不新增 iMessage、Office 的图片能力。

只增加一条共享处理链：渠道传递图片来源 → 在会话工作区保存原图 → 生成模型副本 → 发送图片和原图清单。复用现有文件入站、附件保留时长、会话路由和管理接口机制，不增加后台任务或渠道专用压缩器。

## 设置与行为

入口：**设置 → IM机器人 → 通用设置（齿轮）→ 附件 → 图片输入**。

| 设置 | 默认值 | 作用 |
| --- | --- | --- |
| 原图接收上限 | 30 MB / 张 | 下载和落盘的硬上限，超出时提示用户 |
| 模型单图上限 | 5 MB | 压缩后的单张图片预算 |
| 模型图片总量上限 | 20 MB | 一条消息中图片内容块的合计预算 |
| 每条消息最多图片数 | 20 张 | 图片接收数量上限 |

界面中的 MB 按 1024 × 1024 字节计算。设置为全局配置，影响后续消息；平台和宿主自身的限制仍然生效。企业微信原有的短时链接预取队列容量也保持不变。

- 原图保存到实际 Session 工作区的 `.dsh-im/inbound/`，沿用现有附件清理机制。压缩不覆盖原图。
- 图片副本保持比例、不裁剪、不放大，最多尝试三组尺寸与质量参数。透明图片保留透明度，动画图片不会截成首帧。
- 单图或总量预算不足、压缩失败时，保留原图清单并明确提示模型用工具读取，避免把未提供的图片当成已经看见。
- 宿主明确在受理前拒绝图片（模型不支持、图片大小、总量、数量或像素限制）时，复用已保存原图，以纯文件清单重试一次。超时和未知错误不自动重试。
- `sharp` 是可选依赖；缺失时仍能发送符合大小预算的原生图片，并将大图作为文件提供。
- 配置保存在 `$DSH_HOME/integrations/dsh-im/image-input-settings.json`，校验后原子写入。提高上限可能增加请求体积、处理耗时、磁盘占用和模型成本。

## 本机飞书实测

环境：macOS、Node 24.19.0、DSH 0.1.6-alpha.2；本机机器人 **今天是牢梁**，模型 `doubao-seed-2.1-turbo`。测试图片通过飞书客户端的“图片/视频”入口发送。

样本是一张 2200 × 2000 的 PNG，10,212,864 字节（约 9.74 MiB），包含编号 `SUNSET-4927` 和红色正方形、蓝色圆形、绿色三角形。

| 场景 | 验证结果 |
| --- | --- |
| 默认设置接收超过旧 5 MB 上限的图片 | 成功保存完整原图；宿主接收的模型图片为 1536 × 1396、1,159,702 字节；机器人未调用工具即正确识别编号、形状和颜色 |
| 将单图和总量预算临时调至 1 MB | 本次提示不含图片内容块，只含说明与原图文件清单；机器人调用工具读取原文件，返回正确字节数、尺寸和 SHA256，并回复 `FILE_FALLBACK_OK` |

两个场景保存的原图都与上传文件逐字节一致，SHA256 均为：

```text
f63a8c99320bdfc225fefb2894fd860391e575aa3f46761485acf08f5b489cac
```

两轮 Session 均正常完成，飞书客户端可见实际回复。测试后设置已恢复为 **30 / 5 / 20 MB、20 张**，并通过管理接口及刷新后的设置页面确认；机器人保持连接正常。附件保留时长未改动。

真实平台验证限于飞书；其他渠道的本次验证为自动化测试。宿主拒绝图片后的重试通过自动化测试验证，不把它表述为已逐模型实测。

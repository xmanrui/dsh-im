# Issue #198：微信连接与绑定错误细化方案

日期：2026-09-12。状态：待实施方案，本文件不代表修复已完成。

关联反馈：[Issue #198](https://github.com/xmanrui/dsh-im/issues/198)。方案核对基线：`1040e56`，插件版本 `4.19.2`。

目标：微信掉线、重启后恢复失败、移除失败或重新绑定失败时，用户能知道失败发生在哪一步、可以采取什么操作，并提供一个能在 Host 日志中查到的参考号。维护者可以区分网络、微信接口、凭据、文件存储和 Harness 故障，不再只能看到 `weixin-operation-failed`。

## 1. 已确认的问题与范围

当前信息不足以确认 #198 首次掉线的根因。反馈者没有提供具体版本、运行方式和日志；历史 #73 的 Desktop 兼容故障不能作为这次问题的定论。

已通过代码核对和模拟异常确认以下诊断缺口：

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `WeixinController.startProvisioning()` → 微信 RPC | Controller 识别了网络、超时等错误，但随后抛出；RPC 除工作区错误外一律返回 `weixin-operation-failed` | 四种模拟错误 `network-error`、`timeout`、`http-error`、`invalid-qr` 的返回值完全相同，这条路径没有原始错误日志 |
| `#resolveToken()` | 将凭据读取异常转换成 `undefined` | 存储读取失败被误认为凭据缺失 |
| `initialize()`、`reconnectBot()`、`status()` | 初始化异常及 Runtime 故障被概括成 `connection-failed` | 重启恢复失败、token 失效、Harness 故障无法从账号卡片区分 |
| Runtime / API | 部分错误已有安全分类，但启动、轮询、停止的业务返回码保留不一致 | 无法稳定区分 HTTP 拒绝、微信业务拒绝及底层网络故障 |
| `deleteBot()` | 删除凭据或配置失败后尝试恢复，再抛出通用异常；部分清理错误仅记录日志 | 看不出哪一步失败、移除是否提交、恢复是否成功 |
| Client 重连、移除、错误归一化 | 重连 `catch` 丢弃异常；移除失败只更新读屏播报；归一化只保留 `code/message` | 即使后端细化，前端仍可能丢失信息或没有可见提示 |
| ConnectionSupervisor | 前置 Harness 检查失败时只记录日志，不进入账号初始化 | 账号卡片可能只显示离线，缺少阻止恢复的原因 |

前一轮排查运行了 36 项微信相关测试，全部通过；这证明现有覆盖范围没有失败，不等于复现了反馈者的真实环境。切换机器人工作区目前只修改路径并清理会话映射，没有直接删除微信登录凭据。

本次完整范围是微信管理及连接诊断：首次绑定、扫码轮询、重启恢复、手动重连、连接长轮询、移除接入、工作区保存、渠道启动及状态读取。消息发送继续使用已有 `lastMessageError` 机制；本次不统一改造其他渠道、不修改 DSH 核心、不新增诊断服务器或持久化数据库。

重试间隔、登录有效期、账号删除顺序和工作区切换行为沿用现状。发现真实恢复逻辑问题时另行记录，不能把诊断改进描述为已经解决掉线。

## 2. 错误表示：类别、阶段、原因分开

保留现有 `code`，用 `details.stage` 标明具体步骤，用 `details.reason` 表示经过校验的底层原因。例如申请二维码与恢复连接都可能发生 `network-error`，无需为每种组合新建错误码。

RPC 错误以及 `provisioning.error`、`bots[].error` 使用同一份安全结构：

```json
{
  "code": "network-error",
  "message": "无法生成微信二维码：暂时无法访问微信服务。",
  "details": {
    "operation": "provision.begin",
    "stage": "qr.begin",
    "reason": "ENOTFOUND",
    "hint": "微信服务域名解析失败，请检查运行 DSH 的机器的网络和 DNS 设置后重试。",
    "referenceId": "WX-CONN-8C42A7F1",
    "occurredAt": "2026-09-12T02:00:00.000Z"
  }
}
```

这是合成示例，不是真实用户日志。

字段约定：

| 字段 | 约定 |
| --- | --- |
| `code` | 稳定错误类别；保留已公开的错误码；真正无法分类才使用 `weixin-operation-failed` |
| `message` / `details.hint` | 由固定模板生成的简短说明和下一步操作；支持中英文；不得直接透传任意 `error.message` |
| `details.operation` | RPC endpoint，或内部操作枚举 `startup`、`connection.restore`、`connection.monitor`、`connection.close` |
| `details.stage` | 实际执行步骤，例如 `qr.begin`、`credential.read`、`harness.check`、`connection.poll`、`account.remove` |
| `details.reason` | 白名单内的网络、TLS、文件系统或受控应用原因，例如 `ENOTFOUND`、`ECONNREFUSED`、`EACCES`；无证据时省略 |
| `details.httpStatus` | 仅在实际收到 HTTP 响应时填写 100–599 的整数 |
| `details.providerCode` | 微信业务错误码；不等同于 HTTP 状态；首版仅接收有界的整数或整数字符串，其他值只标为未知业务拒绝 |
| `details.resource` | 可选资源枚举 `credential-store`、`account-config`、`account-state`、`workspace-config`、`workspace-directory`；不放完整路径 |
| `details.referenceId` / `occurredAt` | 首次报告时生成，同一故障向 RPC、账号状态和日志传播时复用；读取状态不生成新编号 |

正常取消、二维码过期和输入验证失败使用明确的现有状态或错误码；不要求都生成故障日志和参考号。请求取消与真实请求超时需要分开判断，不能按错误类名把两者合并。

`schemaVersion` 保持 1；`details` 为增量字段。现有管理 RPC 已支持 `error.details`，旧客户端仍能使用 `code/message`；新客户端必须兼容旧 Host 没有诊断字段的返回。诊断上下文只在当前 Host 内存中保留，不写入账号或凭据文件。

## 3. 首版错误分类

“保留”表示已有错误码继续使用；“新增”表示当前没有足够具体的类别。相同错误码的文案按实际阶段调整，不再在重启恢复时错误地写“微信已授权”。

| 场景 | 错误码 | 处理与提示 |
| --- | --- | --- |
| 网络不可达、DNS、连接重置或 TLS 失败 | 保留 `network-error` | 按受控 `reason` 给出提示；不把 TLS 问题自动归因于代理，也不建议关闭证书校验 |
| 请求超时 | 保留 `timeout` | 标明二维码申请、扫码状态查询或启动连接阶段；记录实际超时配置 |
| HTTP 非成功响应 | 保留 `http-error` | 带 `httpStatus`；401/403、429、5xx 分别提示访问被拒绝、限流、服务异常；不把 HTTP 403 直接解释为 token 失效 |
| 微信拒绝申请二维码 | 新增 `qr-request-rejected` | HTTP 成功但业务码非零时保留 `providerCode`，不再误报为没有二维码 |
| 二维码字段或地址无效 | 保留 `invalid-qr`、`untrusted-qr` | 提示服务返回数据异常；不输出二维码令牌或完整地址 |
| 本机二维码图片编码失败 | 新增 `qr-encode-failed` | 标明已获取扫码地址、本机图片生成失败；用同一安全诊断返回，不自动创建另一轮登录 |
| 响应不是有效 JSON、扫码状态未知 | 保留 `invalid-response`、`invalid-login-status` | 区分响应解析与扫码协议状态问题；不输出原始响应正文 |
| 绑定任务不存在或不处于可验证状态 | 新增 `provision-attempt-not-found`、`provision-state-invalid` | 常见于重启后的旧页面；提示重新读取状态或重新生成二维码 |
| 凭据确实不存在 | 保留 `missing-token` | 只有读取成功且为空才能使用；提示重新绑定 |
| 凭据读取、写入失败 | 保留 `credential-read-failed`、`credential-save-failed` | 标明存储步骤和可用的 `reason`；读取失败不提示用户先删除账号 |
| 删除凭据失败 | 新增 `credential-remove-failed` | 提示本机凭据未确认移除；根据实际结果说明账号保留或恢复状态待确认 |
| 微信明确报告登录失效 | 保留 `stale-token` | 仅在有已识别的微信业务码证据时使用；提示重新绑定，避免只写“稍后重试” |
| 账号配置写入、删除失败 | 保留 `account-config-save-failed`；新增 `account-config-remove-failed` | 区分凭据存储与账号配置，记录 `EACCES`、`EPERM`、`ENOSPC` 等原因 |
| 账号状态加载、保存、清理失败 | 新增 `account-state-read-failed`、`account-state-write-failed`、`account-state-cleanup-failed` | 解析错误、权限错误与磁盘错误分别给出提示；清理失败是否影响主操作由实际提交结果决定 |
| 工作区保存失败 | 保留已有 `workspace-*` 校验错误码；新增 `workspace-save-failed` | 在文件读写位置标明资源，避免把清理会话失败误报成目录不存在 |
| Harness 健康检查或接口调用失败 | 保留现有 `harness-*` 分类 | 说明宿主未就绪、认证拒绝、接口不兼容等；进程内连接不提示检查 HTTP 端口，显式远程连接才使用对应网络提示 |
| 微信启动或长轮询被拒绝 | 保留 `start-rejected`、`updates-rejected` | 带 `providerCode`；启动和轮询都检测有效非零 `ret/errcode`，零值不能遮住另一个字段的非零错误 |
| 停止通知被拒绝 | 新增 `stop-rejected` | 标明远端停止通知失败；不等同于本机账号删除失败 |
| 状态读取失败、运行时准备失败 | 新增 `status-read-failed`；保留 `runtime-prepare-failed`、`connection-start-failed` | 作为对应阶段的保守回退；优先保留更具体的已知原因 |
| 未知异常 | 保留 `weixin-operation-failed`、既有激活未知分类 | 必须携带阶段和参考号，提示反馈诊断信息，不猜测网络或账号问题 |

识别规则必须在知道操作含义的位置执行。禁止通过异常文案是否包含“token”“403”“permission”来推断失效、权限或 HTTP 状态。未知第三方 `.code` 不自动成为公开错误码。

凭据来源“只读”只能基于提供方支持的 `describe()` 返回 `writable: false` 或稳定的结构化拒绝原因判断；提供方没有该能力时保守显示凭据写入/删除失败，不通过字符串匹配猜测环境变量覆盖。

现有 `WeixinApiError` 用于消息与文件发送的分类保持原义。共享的 HTTP 请求补充安全元数据时，需要覆盖已有发送测试，避免意外改变投递结果判断。

## 4. 后端实施路径

### 4.1 微信专用诊断模块

新增 `src/channels/weixin/connection-error.mjs`，集中维护代码目录、阶段校验、固定文案、安全字段提取和参考号生成。参考钉钉已有的“用户错误 + Host 诊断”模式，但不直接复制其任意异常文本输出规则，也不为这一次改动抽象跨渠道框架。

内部仍可用 `cause` 串联异常。公开对象和日志对象均由字段白名单重新构造；安全包装经过 RPC、Controller、Runtime 时不重复包装、不生成另一份参考号。错误处理或日志写入自身失败不得覆盖原操作结果。

### 4.2 API 与 Runtime 保留证据

`weixin-api.mjs` 在请求边界记录固定操作标识、耗时、HTTP 状态和安全业务码；不记录 URL 查询参数、请求体或响应体。复用现有业务拒绝判断的原则，补齐二维码申请、连接启动及停止，不重写消息发送协议。

Runtime 保存结构化的最后连接错误，供 Controller 的账号状态使用；不再依靠 `lastError` 文本反推原因。长轮询故障、启动失败和主动停止分别处理：

- 连接失败后保留最近一次真正阻断连接的诊断；连接成功后清除对应错误。
- 主动关闭或取消产生的中止不显示为新掉线故障；真正的超时仍可诊断。
- 长轮询正常超时目前会转为空结果并继续轮询，保持该行为，不把正常等待显示成故障。
- 停止通知、清理中的非致命错误记录为警告，不能覆盖之前导致掉线的主错误。

### 4.3 Controller 与监督器

将凭据读取的“成功但为空”与“读取异常”分开。`initialize()`、`reconnectBot()` 以及授权后读取旧凭据的步骤使用具体错误；自动恢复失败保留在账号卡片，手动重连失败在 RPC 和卡片中使用同一参考号。

生成二维码前收集旧账号 `localTokens` 属于辅助读取：单个读取失败仍可按现有语义继续申请二维码，但需要记录带账号上下文的安全警告，不能把辅助读取警告冒充二维码申请失败。移除前读取旧 token 失败也必须记录，后续不能声称已经具备完整回滚依据。

ConnectionSupervisor 在前置 Harness 检查失败时，将同一诊断交给 Controller 的连接状态呈现。不得因此把仍在健康轮询的微信连接统一标成断线；只解释本轮恢复被 Harness 阻止的账号。保持现有重试节奏，文案根据实际原因说明需要人工处理或可以稍后重试。

渠道生产初始化阶段已有 `weixin-startup-config-invalid`、`weixin-startup-permission-denied` 等分类，继续保留。通过共享启动器的可选错误格式化回调为微信补上参考号与安全日志，其他渠道走原默认实现。账号状态 JSON 无效应在其读取边界包装，避免全部误称为 `config.json/workspaces.json` 错误。

如果 DSH 的凭据服务自身启动失败，导致微信插件根本没有被注入和执行，本方案不能让一个未加载的插件返回错误；该情形仍需 DSH 启动日志，不能承诺账号卡片覆盖宿主全部故障。

### 4.4 移除与回滚：报告实际结果

主错误必须保留，回滚失败作为关联诊断，不能覆盖原错误。日志记录已完成的步骤，以及 `rollback` 为 `succeeded`、`failed`、`not-attempted` 或 `unknown`；只在有成功返回或可靠回读依据时声称恢复成功。

特别注意 `observeBotWorkspaceRemovals()` 可能在账号配置已删除后继续清理工作区，之后才抛错。不能只凭 `remove()` 抛异常，就断言账号配置仍存在。

| 实际结果 | 前端结果 |
| --- | --- |
| 删除凭据或配置失败，账号仍存在 | `ok: false`，显示失败步骤；按已确认的回滚结果给提示 |
| 账号移除已提交，但状态文件或工作区清理失败 | 返回已确认的最新账号状态，并通过可选 `warnings` 呈现清理问题；不把已移除的账号重新显示为可用 |
| 操作提交后刷新状态失败 | 返回 `status-read-failed`，在固定提示中说明移除可能已完成，需重新读取；不引导连续重复删除 |
| 本机账号删除成功，远端停止通知失败 | 成功状态附安全警告，不冒充删除失败 |
| 回滚失败或最终状态无法确认 | 明确“当前状态未确认”，显示参考号；不声称已恢复或已断开 |

`warnings` 只用于该次操作的非致命诊断，由新 Client 归一化展示，旧 Client 忽略；不增加自动删除、自动重新扫码或重新启动连接的动作。移除完成后账号卡片会消失，因此警告必须能保留在微信页面的可见操作反馈区。

### 4.5 RPC 作为最后的安全出口

`rpc.mjs` 使用诊断模块替换无条件 `internalFailure()`；保留现有参数校验与工作区错误。已分类错误直接通过字段白名单输出，未分类错误补上 operation、stage 和参考号。

二维码编码异常单独包装。`provision.begin` 的失败要保留原始分类，`provision.poll` 与验证请求的失效任务要返回明确代码。既有终态、取消和过期行为不被改写为内部错误。

## 5. 日志和可复制诊断

Host 使用单行结构化日志，固定前缀 `[dsh-weixin]`，与 UI 共用参考号。示例：

```text
[dsh-weixin] {"event":"connection-failure","referenceId":"WX-CONN-8C42A7F1","operation":"provision.begin","stage":"qr.begin","code":"network-error","reason":"ENOTFOUND","durationMs":103,"pluginVersion":"4.19.2"}
```

允许记录：时间、参考号、受控操作/阶段/资源、经过格式校验的本机 botId 或 attemptId、HTTP 状态、安全业务码、底层原因、耗时、回滚结果，以及实际取得的运行版本、平台和 Node 版本。插件版本来自当前运行构建；Harness/Desktop 版本只通过已有可信运行元数据获取，获取不到就省略，不能使用 npm 最新版本代替。

不输出：`bot_token`、`local_token_list`、登录二维码令牌/URL/图片、配对码、消息 `context_token`、用户账号原始 ID、请求/响应正文、Authorization、代理地址及密码、完整环境变量、完整文件路径和会话内容。即使字段名字叫 `providerCode`，也必须校验值，不能用宽泛字符串正则假定它安全。

错误链最多读取 4 层并检测循环；只提取白名单原因与类型。未知异常若需要定位代码，可保留确认属于插件文件的相对文件名和行号，丢弃 stack 第一行、任意函数名、完整路径及无法安全解析的 frame；不直接打印原始 Error 或 stack。标准错误码比不受控异常文本优先。

由首次将故障转为公开诊断的模块记录一次；上层传播不重复记完整错误。相同账号、阶段、错误类别、原因及 HTTP/业务码的自动恢复失败在 60 秒内合并，并复用已写入日志的参考号，记录重试次数；不能生成一个新的页面参考号却把对应日志去重掉。原因改变、手动操作或恢复成功单独记录。去重状态按账号/操作有界保留，账号移除及 Host 关闭时清理。去重只影响日志量，不延后连接重试、不影响卡片当前错误。

页面“复制诊断信息”复制公开错误字段、发生时间和可用版本。默认不复制 botId、attemptId、工作区路径或任何原始日志，也不向 GitHub 自动发送。剪贴板不可用时显示可选择的纯文本。

## 6. 前端呈现

新增微信内部使用的错误展示小组件；沿用现有页面样式，避免为排障重做设置页。普通用户默认看到说明和操作提示；错误码、阶段和参考号放在可展开详情中。

示例：

```text
无法生成微信二维码
微信服务域名解析失败，请检查运行 DSH 的机器的网络和 DNS 设置后重试。

诊断详情
错误码：network-error
失败阶段：申请二维码
底层原因：ENOTFOUND
参考号：WX-CONN-8C42A7F1

[重新生成二维码] [复制诊断信息]
```

具体落点：

| 入口 | 改动 |
| --- | --- |
| 绑定失败面板 | 按阶段显示“无法生成二维码”“查询扫码状态失败”“微信授权后连接失败”等标题；不能对所有错误都只写“微信没有绑定完成” |
| 账号离线摘要 | 展示最近一次连接失败的具体原因、建议及可复制诊断 |
| 检查/重试连接 | `catch(error)` 保留诊断，不再替换成“连接检查失败，请稍后重试” |
| 移除确认区域 | 在页面中显示可见错误并保留必要操作入口，同时继续读屏播报；成功后的警告显示在页面反馈区 |
| 工作区保存 | 编辑器保留原有输入校验，文件保存失败展示具体资源与参考号；不自动操作微信登录 |
| 状态读取失败 | 明确说明“状态读取失败，以下是上次状态”，避免把无法读取状态渲染成确定掉线 |

`unwrapRpcResult()`、`presentError()`、`normalizeProvisioning()` 和账号归一化共用一个白名单归一化函数，保留安全 `details`；不能靠展开 `...error.details` 回传未知字段。错误、警告和复制文本使用同一归一化结果。更新 Host 的微信翻译表与 Client `i18n.js`；机器错误码和参考号不翻译。

另外区分“Host 已返回微信业务错误”和“管理请求本身没有成功”。后者在客户端使用 `weixin-management-unreachable` 或 `weixin-management-invalid-response`，根据实际证据选择，不能包装为微信服务器故障。若 Host 没有返回参考号，页面写明没有取得 Host 诊断；复制失败时间、操作和已知版本，不伪造一个无法查到的服务端参考号。主动取消不归入这些失败。

## 8. 验证与验收

测试使用临时目录、测试凭据和注入的网络/文件故障，不依赖真实微信服务故意出错。

| 测试组 | 必须验证的行为 |
| --- | --- |
| 二维码失败 | DNS、连接拒绝、TLS、超时、HTTP 403/429/500、无二维码字段、图片编码失败能够区分；RPC 与日志参考号一致 |
| 微信业务失败 | HTTP 200 + 非零 `ret/errcode`；数值与字符串零；一个字段为零、另一个非零；不把无凭据证据的 HTTP 错误分类成 token 失效 |
| 凭据与文件 | 读取异常和缺失分开；写入/删除失败、只读来源的已确认拒绝、非法 JSON、磁盘满等按资源和阶段显示；不靠异常文案猜测 |
| 自动恢复 | 重启加载配置后凭据读取失败、Harness 前置失败、notifyStart 拒绝、轮询 token 失效均进入正确诊断；恢复成功清除错误；健康账号不被另一账号故障覆盖 |
| 移除与回滚 | 删除凭据失败、配置删除失败、配置已提交后清理失败、回滚失败、状态刷新失败均如实报告；不把警告变成假失败或把未知状态变成假成功 |
| 取消与轮询 | 用户取消、页面卸载、Host 关闭、正常长轮询超时不产生虚假红色故障；扫码请求真正超时可见 |
| 信息安全 | 在异常 message、cause、stack、code、providerCode、URL、代理信息及响应中放入合成秘密；RPC、账号状态、警告、复制文本和捕获日志都不包含秘密；覆盖循环 cause 和日志器抛错 |
| 兼容与 UI | 原生管理 RPC 能传递 details；旧 Host 没有 details 仍能显示；错误详情不会被归一化丢弃；重连和移除错误可见；中英切换、复制失败回退可用；管理传输失败不伪造微信服务错误或 Host 参考号 |
| 现有业务 | 正常绑定、重启恢复、工作区切换、消息收发、删除、已有发送失败诊断继续通过；确认重试及账号写入顺序未因诊断改变 |

先运行新增故障测试与微信现有测试，再验证共享 startup、management-rpc、工作区存储及 i18n 相关测试。完成实现后运行仓库要求的 `npm run check` 和 `git diff --check`，并对二维码失败、离线账号、移除失败三个真实渲染场景做浏览器检查。

不以模拟测试宣称真实 #198 已复现；不为验收主动删除现有机器人的真实凭据。发布后的排查材料应包含：失败时的操作步骤、Desktop/Web 运行方式、实际版本、页面复制的诊断，以及相同参考号的 Host 日志。

最终验收标准：反馈者再次遇到问题时，至少能明确指出失败步骤、错误类别及日志参考号；已知网络、凭据、存储和 Harness 错误不再全部变成 `weixin-operation-failed`。拿到新证据后，再对 #198 的掉线根因做单独判断。

## 9. 实施记录（2026-09-12）

主要落点：

- `src/channels/weixin/connection-error.mjs` 集中生成固定文案、受控原因、参考号和安全日志；`diagnostic-details.mjs` 为两端共用的字段白名单。

# Issue #228：多渠道错误原因提取与页面提示方案

日期：2026-09-20。状态：待实施；本文是方案，不代表代码已修改或现场网络故障已解决。

关联反馈：[Issue #228](https://github.com/xmanrui/dsh-im/issues/228)。范围依据当前设置页中的 13 个接入入口，包含实验功能和邮箱。

## 1. 目标与实施原则

用户遇到失败时，页面能够回答三件事：**哪一步失败、已知的原因是什么、接下来该做什么**。复制出的诊断应足够让维护者继续排查；原因未知时明确说明，不能只给一个没有进一步证据的参考号。

采用一个简单做法：**把微信已有诊断能力中通用的部分提取出来，让其他渠道接入；渠道已有的专用错误解释继续保留。**

- 沿用 `code`、`message`、`details`、现有账号错误状态和 Host 日志，不另建错误协议、诊断服务、数据库或监控系统。
- 沿用各渠道 Controller、Runtime、SDK 和连接流程，只修补丢失异常、错误归类、传递及展示的位置。
- 消息处理继续使用 `message-failure.mjs` / `lastMessageError`，连接测试继续使用 `testMessage`；按需补充可选诊断字段，不另建平行机制。
- 不顺带调整重试策略、自动重新扫码、删除顺序、平台权限或网络代理配置。诊断只能说明失败，不能声称修复了真实网络故障。
- 不一次性统一各渠道所有业务错误码，不重写现有设置页。

### 3.2 操作覆盖

各渠道已有的以下入口都必须检查，包含抛出的异常和后台任务写入的错误状态。

| 操作 | 错误进入哪里 | 页面位置 |
| --- | --- | --- |
| 插件启动、配置加载、重启恢复 | 启动错误或对应账号 `error` | 渠道页顶部 / 账号卡片 |
| 扫码、凭据绑定、授权查询 | RPC 错误和绑定任务 `error` | 绑定表单或扫码区域 |
| 已授权后的保存、运行时初始化、Harness 检查 | 绑定任务或账号 `error` | 明确“授权完成，但后续步骤失败” |
| 手动重连、后台建连 / 轮询 / 恢复 | RPC 错误或账号 `error` | 账号卡片；无按钮操作也可见 |
| 连接测试 | 原 `testMessage`，附可选 `error` | 连接测试结果；不据此把账号改成离线 |
| 移除、清理、回滚 | RPC 错误或现有操作警告 | 操作反馈区域；卡片消失后警告仍可见 |
| 工作区、模型、Preset、访问设置等已有管理操作，以及状态 / 权限读取 | 保留已有具体错误，附诊断 | 对应设置或渠道反馈区域 |
| 消息接收处理、模型调用、回复发送 | 原 `lastMessageError` / 已有投递失败机制 | 原消息错误位置；补充可复制详情 |
| 浏览器访问 DSH 管理接口失败 | Client 管理连接错误 | 渠道页；不解释成第三方平台故障 |

文档中的渠道表与操作表就是实施检查表。每个适用组合必须注明测试落点；不适用项写明原因，不以空白代表已经覆盖。无需新增运行时“覆盖注册表”。

公共 reporter 沿用微信返回包装异常及 `.publicError` 的模式，调用方可以保持原有 `throw` / 状态保存方式。通过现有 `options` / `internals` 注入同一个渠道 reporter，覆盖启动、Controller、Runtime 和 RPC；初始化失败时也能取得 reporter。

## 5. 原因提取规则

### 5.1 提取原始证据

- 同时遍历 `cause` 与 `AggregateError.errors`；兼容 SDK 上实际存在的 `errors` 数组。最多检查 16 个异常节点，用 `Set` 防止循环，到限额标记 `truncated`，避免无限展开。
- 按固定顺序读取受控的 `code`、`status` / `statusCode` / `response.status`，以及已有渠道适配器认可的业务码。多个底层原因去重保留。
- 一个原因时沿用 `details.reason`；多个不同原因时使用 `reason: multiple-causes` 和 `reasons` 数组，页面并列展示，不能随意选择一个当作唯一根因。
- 仅有包装错误、未知代码或没有结构化证据时使用 `reason: unknown`。保留已知业务解释，不靠不受控错误文本推断用户该删除账号或改代理。
- 请求地址、操作阶段、耗时从发起操作的位置提供；不从任意异常文本中抽取 URL。已知平台的公共域名可进入详情，自定义邮箱 / Office / Harness 地址默认只显示服务类型。
- 在会重新包装异常的 API / SDK 边界保留 `cause`；SDK 事件提供错误对象时传给原有状态处理。缺失的原始异常无法靠 RPC 末端恢复。

### 5.2 分类和提示优先级

先保留调用位置确认的失败阶段、已有业务语义和操作结果，再用通用证据补充原因。网络原因不能把“保存文件失败”改成“二维码失败”，也不能把“发送结果不确定”改成“消息未发送”。

| 证据 | 页面解释与建议 |
| --- | --- |
| `ENOTFOUND` / `EAI_AGAIN` | 域名解析失败；检查运行 DSH 的机器的 DNS 和网络 |
| `ECONNREFUSED` | 连接被拒绝；检查目标服务 / 配置端口及访问限制，不能直接断言是代理 |
| `ECONNRESET` / `EPIPE` / SDK 明确的连接中断 | 连接中断；检查网络和服务状态，结合现有重试状态提示 |
| `ENETUNREACH` / `EHOSTUNREACH` | 网络或目标不可达；检查路由、出口和访问限制 |
| `ETIMEDOUT`、Undici 超时代码、插件计时器到期 | 请求超时；显示已知的耗时和超时阈值，区分连接超时与等待响应超时 |
| 受认可的 TLS / 证书错误码 | 证书或 TLS 校验失败；检查系统时间、证书链及相关网络配置 |
| HTTP 407 或 SDK 明确代理错误 | 代理连接 / 认证失败；检查 DSH 进程使用的代理配置；不输出代理凭据 |
| HTTP 401 / 403 | 请求被拒绝；保留已有能确认 Token 或权限问题的平台业务分类，否则不推断“登录失效” |
| HTTP 429 / 明确平台限流码 | 服务限流；按既有行为稍后重试，不新增自动重试 |
| HTTP 5xx / 平台业务拒绝 | 服务异常或业务拒绝；展示受控状态 / 业务码及已有平台建议 |
| 非法 JSON / 非预期响应 | 服务响应无效；与网络不通、配置文件 JSON 错误分开 |
| 凭据、文件、配置、系统权限、SDK 初始化错误 | 复用已有资源及阶段解释，例如“读取登录凭据失败”“iMessage 权限未授予” |
| 多个原因 / 未识别原因 | 明确列出多个原因或说明原因未知，提供详情和参考号；不统一写成“检查网络” |

文件权限、HTTP 权限、系统权限分别由实际操作上下文解释。已有钉钉特殊依赖判断、Telegram Webhook 冲突、Discord Intents、QQ 状态损坏等优先保留。

取消、页面卸载、Host 关闭、正常长轮询到期、授权仍在等待均保持现有正常状态。只有真正失败才生成故障诊断；二维码过期继续提示重新获取二维码。

## 6. 错误结构与兼容

沿用 `{ code, message, details }`。不新增协议版本，不强制把各渠道旧 `code` 全部改名。通用原因放在 `details`，旧的通用失败代码也可以配上准确提示。

示例（字段按实际证据填写）：

```json
{
  "code": "network-error",
  "message": "无法申请微信二维码：微信服务域名解析失败。",
  "details": {
    "channel": "weixin",
    "operation": "provision.begin",
    "stage": "qr.begin",
    "reason": "ENOTFOUND",
    "service": "weixin-api",
    "host": "ilinkai.weixin.qq.com",
    "durationMs": 103,
    "timeoutMs": 10000,
    "referenceId": "WX-CONN-8C42A7F1",
    "hint": "请检查运行 DSH 的机器的网络和 DNS 设置后重试。"
  }
}
```

已有的 `occurredAt`、`pluginVersion`、`httpStatus`、`providerCode`、`resource`、配置文件 / 字段及回滚信息继续保留。新增字段全部可选；Node、平台和 DSH 版本只在实际取得时附加，DSH 版本缺失时不能用插件版本或最新发布版本代替。

兼容处理：

- 保留微信 `WX-CONN`、钉钉 `DT-CONN` 和消息失败 `MF` 参考号；其他连接故障使用 `IM-CONN`，通过 `channel` 区分，不增加每个渠道一套编号规则。
- 钉钉旧的顶层 `hint/referenceId` 继续可读；新前端归一化到同一显示结构，原专用错误包装的判定方式一并适配。
- `bots[].error`、绑定任务 `error`、RPC 错误和警告都必须走同一安全归一化；不能只改 RPC 的失败返回。
- `lastMessageError` 保留现有 `code/reason/message/referenceId/at`，仅附可选 `details`。显示时由公共组件适配这些字段；同一事件保留已有参考号，不再次独立报告。
- `testMessage` 保留 `sent/code`，失败时可附 `error`；`test-target-unavailable` 仍说明需要先有可测试的会话，不能误报网络故障。
- 新 Client 接收旧 Host 的 `code/message` 时照常显示；新 Host 返回额外字段时旧 Client 保持基本提示。沿用管理接口要求的 `details: {}` 兼容行为。

## 7. 从底层到页面的接入方式

1. **API / SDK 边界**：保留原始 `cause` 和受控的状态 / 业务码；必要时附真实请求耗时、服务类型。不要为了采集诊断改写所有 HTTP 客户端。
2. **Controller / Runtime**：在知道失败阶段、即将保存公开状态的位置调用 reporter，保存 `.publicError`；后台事件、恢复及轮询使用相同入口。禁止用一个新的通用 `{code, message}` 覆盖已有诊断。
3. **RPC**：已有诊断直接保留，未报告的异常才兜底补 `operation`、已知阶段和参考号。拿不到具体阶段时使用操作级描述，不猜测成 `qr.begin` 或 `harness.check`。
4. **Client API**：`unwrapRpcResult`、`presentError`、账号 / 绑定任务归一化都保留安全 `details`；优先改共享 `token-api.js`，再补独立渠道。`catch` 不能只存 `error.message`。
5. **页面**：绑定区域、账号卡片、操作反馈复用公共错误组件；成功后按原逻辑清除对应错误，不清除其他账号或其他操作的错误。

浏览器调用 DSH 管理接口失败属于单独的 `management.request` 阶段：复用微信现有处理并通用化。在宿主提供结构化 HTTP 状态时保留 401 / 403 / 404 / 405 / 5xx 等；拿不到时只说明管理连接失败，不从异常字符串猜测状态。没有进入 Host 的错误不生成虚假的 Host 参考号。

原生管理 RPC 的最后兜底只处理逸出的异常，保留认证、Host / Origin、权限和请求校验。不得将所有 HTTP 403 改写为平台权限问题。

## 8. 页面提示

复用现有“简短提示 + 处理建议 + 诊断详情 + 复制诊断信息”，不新增专门诊断页面或弹窗。

| 场景 | 默认可见文案示例 |
| --- | --- |
| 微信 DNS 失败 | 无法申请微信二维码：微信服务域名解析失败。请检查运行 DSH 的机器的 DNS 和网络。 |
| 钉钉证书失败 | 无法申请钉钉二维码：TLS 证书校验失败。请检查系统时间及证书配置。 |
| QQ 保存失败 | QQ 已完成授权，但本地状态保存失败。请检查数据目录权限和磁盘空间。 |
| 邮箱认证失败且有明确业务证据 | 邮箱登录验证失败。请检查账号和授权信息。 |
| 管理连接失败 | 无法访问 DSH 的管理接口。请检查 DSH 连接或重新登录后重试。 |
| 未知异常 | 微信二维码申请失败，暂未识别具体原因。请复制诊断信息，并查看相同参考号的 DSH 日志。 |

详情展示实际取得的阶段、原因 / 多原因、服务、HTTP / 业务码、耗时、版本、时间和参考号。不展示空字段；未知原因明确显示“未识别”，不能因缺少 `reason` 而静默消失。

复制保留现有纯文本格式和剪贴板失败回退。中英文沿用现有 i18n，复用公共组件现有样式；窄屏长代码可换行。

状态语义保持准确：移除已经提交时展示清理警告；发送结果不确定时提醒先检查是否收到；连接正常但测试消息发送失败时，只展示测试失败。

## 9. 日志：参考号必须能提供额外证据

沿用 Host 结构化日志。日志包含公开诊断，并额外保留有界、脱敏后的异常证据列表，例如每层认可的错误类型、系统原因码、HTTP 状态和平台业务码，以及 `cause` / `errors` 是否存在、是否截断。

对于没有认可原因码的异常，记录固定的 `unknown`、标准错误类型（如 `TypeError`）、已知操作位置 / 服务、实际取得的耗时与版本。任意自定义异常名称和代码不能仅凭字符格式正确就直接输出。完全没有底层证据时如实记录，不承诺仅凭日志就能确定根因。

公开详情和日志均不输出令牌、二维码内容、配对码、请求 / 响应正文、消息内容、完整 URL、代理密码、完整环境变量或原始堆栈。沿用安全字段白名单，业务码只接受已认可的数值范围或渠道枚举。需要进一步扩大保留范围时，添加具体的安全字段，不改成直接打印 Error。

首次转成诊断时生成参考号和日志，上层传播不重新生成。复用微信现有自动重试合并机制：按渠道实例、账号 / 绑定任务、操作、阶段和原因区分，状态有界保存；原因变化产生新诊断，恢复 / 移除清除对应记录。多个账号的失败不能互相合并。

消息路径已经有参考号时把附加证据写到原日志事件中。日志写入失败不得影响业务结果。取消和正常等待不记录为错误。

## 11. 测试与验收

采用“公共原因规则充分测试 + 每个渠道接入验证 + 关键流程端到端验证”，避免为所有组合机械复制整套测试。

### 11.1 公共原因规则

必须包含：普通系统错误、`TypeError → cause → 底层错误`、多个 `errors` 分支、超过原四层的包装、循环引用、达到节点限额、未知代码、没有 `code/cause`、HTTP / 业务拒绝、解析异常、TLS、超时及取消。

断言原因是否保留、多个原因是否列出、未知是否明确、分类是否符合实际阶段；在异常各字段加入合成敏感信息，验证页面、复制文本和日志均不泄露。不能只检查参考号格式或错误对象存在。

### 11.2 各渠道接入验证

对渠道表逐项使用实际 API / Runtime / Controller / RPC 和 Client 归一化代码，在外部网络或 SDK 边界注入故障，避免直接伪造最终公开错误：

- 每个渠道至少覆盖一次网络 / 本地连接失败、一个自身特有错误、一个未知错误；无网络连接的操作用对应的本地错误代替。
- 同步绑定失败、后台恢复 / 轮询失败分别验证，检查写入状态的错误与直接 RPC 返回均不会丢失字段。
- 共享代码可使用参数化测试，但独立 RPC、独立 Client 归一化和专用权限 / 授权入口仍须各自执行。
- 连接测试、管理配置、删除 / 清理以及消息处理路径按适用情况检查；保留已有成功、取消、回滚、恢复后清错测试。
- 验证同一故障的参考号从 Host 日志到页面一致、不会重复记录；自动重试合并不混淆账号。
- 每个适用入口都记录对应测试，不以“已抽公共模块”替代接入检查。

### 11.3 页面与兼容

使用真实组件和已接入的归一化链路，检查至少四种代表页面：扫码绑定、Token 绑定、邮箱 / 本地权限、Office。覆盖长原因、多个原因、未知原因、无 Host 参考号、复制失败、删除后警告、中英文和窄屏。

旧 Host 仅返回 `code/message`、钉钉旧顶层字段、现有 `MF` 消息错误均可正常显示。模拟测试和本机浏览器验证应标明范围，不声称复现了反馈者的真实网络环境。

实施完成后运行相关新增测试、现有渠道测试及仓库 `npm run check`、`git diff --check`。完整回归通过后，仅在新的修改或失败需要时重跑。

### 11.4 交付标准

1. 所有 13 个入口的适用操作都有覆盖记录；后台失败与管理请求失败同样可见。
2. 有明确原因的异常，不会在 API → 状态 / RPC → Client → 页面 / 复制任一环节变回无原因提示。
3. 未知异常明确显示未知；日志保留安全的异常结构及真实操作上下文，能够支持下一步排查，不伪造具体根因。
4. 各渠道特有恢复建议、旧格式兼容、脱敏和参考号关联继续有效。
5. 正常等待 / 取消不会变成故障；已有连接、消息处理、重试、删除及回滚行为不因诊断改造改变。

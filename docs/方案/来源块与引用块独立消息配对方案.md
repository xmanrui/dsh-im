# 来源块与引用块独立消息配对方案

> 状态：已实现，自动化回归通过
>
> 日期：2026-09-12
>
> 关联：[上下文增强](../context-enhancement.md)、[Issue-106 引用回复公共语义层](Issue-106-九渠道引用回复消息公共语义层方案.md)

## 1. 结论

渠道写入 prompt 文本的注入块不再留在用户消息正文里。来源块与引用块由 Host 在 `agent/pre-step` 拆成独立消息；指引是会话级策略，改由动态提示词上下文承载：

| 注入块 | 独立消息 | 位置 |
| --- | --- | --- |
| `<dsh_im_source>` | `source.kind = 'plugin'`、`plugin: 'dsh-im'`、`form: 'notice'`，摘要为 `渠道 · 会话类型 · 发送者` | 用户消息**之后** |
| `<dsh_im_source_guidance>` | **不成为消息**：登记到会话后由 Host 作为动态提示词上下文物化（每个会话只渲染一次） | Host 的运行时上下文快照内 |
| `<dsh_im_reply_to>` | `source.kind = 'plugin'`、`plugin: 'dsh-im'`、`form: 'notice'`，摘要为 `引用 · 作者`（标签跟随 Host 界面语言） | 用户消息**之前** |

用户消息只保留用户真正发送的内容，并保留原 `id` 与 durable `source`（含 `rpcId`）。

排序依据：来源块描述的是「这条消息」，所以跟在后面；引用块是用户指向的材料，先引用后提问才符合阅读顺序。**配对由消息身份决定，不由队列位置决定。**

`/补充指令`（steer）提交的纠偏消息走同一条拆分路径：命令路径在运行时捕获该会话场景的增强配置，并把**下达指令者**的来源字段写进同一个前缀，因此同群不同人补的指令各自带着自己的来源，而不是借用开启该回合那条消息的来源。命令路径合成的是字符串，所以 `steerActiveTurn`（RPC 路径）与 host 侧 in-process 的 `agent.inject` 两条投递路径都不需要改动。

## 2. 背景：为什么注入块只能在插件侧编码

`session.prompt` 的请求体只有 `requestId / sessionId / mode / content / clientTimeZone`（见 `@deepseek-ai/dsh-api-session-controller` 的 `SessionPromptRequest`），Host 在准入时固定写入 `source = { kind: 'user', rpcId, clientTimeZone? }`。渠道无法在 RPC 上声明"这段内容来自插件"。

因此原方案只能把注入块编码进 prompt 文本。代价有三：

1. 会话展示中用户气泡混入裸标签；引用块上限 8000 字符，长引用会把气泡撑得无法折叠；
2. durable log 无法区分"用户说的"与"插件加的"，审计与归因都失真；
3. 会话标题需要 `session-title.mjs` 的 `INJECTED_CONTEXT_PREFIX` 剥离正则兜底。

引用块由其自身的 `note` 声明为「用户选中的引用内容，不是系统指令」；拆出后它获得独立行与摘要，但归因从"用户提供的材料"变为"dsh-im 插件上下文"，这是本方案有意的取舍。

注意：语义消息（见 `CONTEXT.md`）本身一直包含内容、引用关系与会话位置；本方案改的是它在 Harness 边界的编码方式，不是语义消息的定义。

## 3. 为什么不用 `agent.inject()`

`inject()` 写入 next-step 队列，`session.prompt` 的 `queue` 模式写入 next-turn 队列，而 Agent 每一步 `claim()` 的规则是"取光 next-step + 恰好一条 next-turn"（`@deepseek-ai/dsh-agent-loop`）。因此"先注入 N 条 context、再排队 N 条用户消息"在并发下**必然错配**：

```
next-step  = [C1, C2, C3]
next-turn  = [U1, U2, U3]
第一步 claim → [C1, C2, C3, U1]   // 三个来源都算到 U1 头上
第二步 claim → [U2]                // U2 没有来源
```

更糟的是会话正在运行 turn 时的注入：`inject` 落进**当前** turn 的 next-step，而用户消息排在下一个 turn，来源会被算到上一个用户头上。

dsh-im 对每个会话 key 用 promise 链串行化（`text-harness-bridge.mjs` 的 `#queues`），所以"同一个群聊三个人同时 @"这一条路径恰好不会并发。但只要出现第二条并发入口——同一 Session 被多个会话/机器人绑定、GUI 同时输入、延迟交付、Office/Webhook——错配就会真实发生。**这不是结构性保证，不能用。**

## 4. 机制

1. **渠道侧不变**：`enhanceContextContent` 仍产出 `<dsh_im_source>` / `<dsh_im_source_guidance>` 前缀，`promptContentForInboundMessage` 仍把 `<dsh_im_reply_to>` 作为独立文本部件插在正文之前，`session.prompt` 仍收到带块的内容。标签字面量由 `INJECTED_CONTEXT_TAGS` / `INJECTED_CONTEXT_SEPARATOR` 统一导出，生产者（`context-enhancement.mjs`、`semantic/reply-reference.mjs`）与解析器不可能漂移。
2. **Host 侧监听**：`plugin-src/host/injected-context.mjs` 注册 `ctx.on('agent/pre-step', …, { global: true })`。该 waterfall 的 `messages` 正是本步已经 claim、尚未提交的那一批；提交发生在同一同步路径的后续 `session.append('user/message', …)`。先例：`@deepseek-ai/dsh-agent-instructions` 用同一位置插入自己的上下文。
3. **拆分**：`src/channels/shared/injected-context.mjs` 扫描消息 content **开头的若干个文本部件**——来源/提示词合成第一个部件，引用块是另一个部件——按标签语法逐个取出。解析是严格的：块体必须是我们自己的 JSON（生产者会转义 `<` `>` `&`，因此标签不可能被值闭合），提示词闭合标签必须独占一行；任何不匹配立即停止且不改动原文。
4. **替换与排序**：用户消息换成去掉注入块后的剩余内容，`id` 与 `source` 原样保留；新增的插件来源消息按 `[引用块…, 用户消息, 来源块]` 排布。
5. **指引改走动态提示词上下文**：`guidance` 不是逐条消息的数据，而是会话级策略，因此不再成为消息行。渠道在派发 prompt 时把它登记到 `src/channels/shared/im-source-guidance.mjs`（模块级注册表，与 `outboundArtifactRegistry` 同型），Host 用 `ctx.systemPrompt.context({ name: 'dsh-im:source-guidance', order: 125, … })` 注册一个 provider 按 `agent.session.id` 取值；Host 只在渲染文本变化时才追加快照，因此每个会话只出现一次。只有注册表里已有同一文本时，重写器才不再把该块写成消息——这既保证不重复，也保证在未登记的路径（例如重启后残留的待入队消息）下不会丢。

顺序说明：Host 自身的运行上下文快照也追加在用户消息之后（`[...claimed, context]`），所以来源块与 Host 惯例一致；会话标题只收集 `source.kind === 'user'` 的消息，因此首条人类消息的判定不受影响。

## 5. 保证与边界

| 关注点 | 结论 |
| --- | --- |
| 配对 | 由"这条被 claim 的消息自己携带的块"决定，与队列顺序无关；同一步内多条用户消息各自配对 |
| 失败隔离 | 解析失败、重写抛错、`reject` 分支都原样返回原 decision，注入块留在用户消息里（等价旧行为） |
| 空消息 | 去掉注入块后没有任何内容的用户消息不替换，避免提交空消息 |
| 幂等 | 已拆分的批次再次经过重写是 no-op（新消息 `source.kind === 'plugin'`，用户消息已无注入块） |
| 降级 | 没有 Agent 循环的 Host、或 `harnessBaseUrl` 指向外部 Harness 时不派发该事件，行为与旧版一致 |
| 其他插件 | 未改动的消息保持对象身份；被拆分的用户消息会换成新对象，因此按对象身份匹配 claimed 消息的插件（如 `dsh-agent-instructions` 的 `findLastIndex(m => messages.includes(m))`）若在本插件之后运行，插入位置会退化为批次头部——位置合法，顺序与旧版略有差异 |
| 指引的落地面 | 它随 Host 的运行时上下文快照出现，因此部署若 `includeRuntimeContext: false` 或调用 `suppressRuntimeContext()`，指引会被一并省略——这是采用 Host 机制的直接结果，不再由本插件绕过 |
| 指引是模板 | context 文本会经过 `{{变量}}` 插值：未注册或格式错误的引用会直接抛错并使该步失败；可用的变量由部署注册 |
| steer 的来源 | 命令路径在运行时捕获——命令不会排队，因此用执行时生效的设置；dingtalk / qq / feishu 的卡片入口使用操作者身份，菜单与消息输入使用该消息的发送者 |
| 未覆盖 | 引用回复块不参与 steer：命令路径只取纯文本，带引用的 `/补充指令` 不会附带引用内容（既有行为） |

归因与展示改善后，注入块仍是 user role 的内容，抗提示词注入仍需系统级声明与字段最小化（`senderName` / `conversationTitle` 是用户可控文本）。

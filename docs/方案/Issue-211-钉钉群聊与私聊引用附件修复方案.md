# Issue #211：钉钉群聊与私聊引用附件修复方案

日期：2026-09-16。分析基线：`0902a1c` / v4.20.2。实施基线：`03d18e9`。状态：修复、自动化检查、群聊和私聊真机验收均已完成。

需求来源：[Issue #211](https://github.com/xmanrui/dsh-im/issues/211)。用户确认的范围是引用附件，包含图片和普通文件；群聊、私聊均需覆盖。实现要求：简单、复用现有代码和机制、控制对其他功能的影响。

## 1. 修复目标

用户引用一条带附件的消息并继续提问时，将附件的实际内容交给当前会话的模型或工具读取，同时保留引用文字、作者及附件摘要。

| 范围 | 目标行为 |
| --- | --- |
| 群聊 | 引用附件并按现有规则 @ 机器人后，实际读取附件 |
| 私聊 | 引用附件后，实际读取附件 |
| 图片、富文本中的图片 | 进入现有 `images` 链路；富文本保留全部有效图片 |
| PDF、Word、Excel、TXT、ZIP 等文件 | 进入现有 `files` 链路，落到当前 Session 的工作区，供工具读取；不按文件后缀限制范围 |
| 音频、视频附件 | 平台提供可下载资源时作为普通文件交给工具；不增加转写、转码或专门的媒体分析系统 |
| 无法取得附件 | 明确提示附件读取失败及可采取的操作，不能把类型/名称摘要当作读取成功 |

“能读取附件”的验收对象是下载字节、模型图片输入或工作区文件；不以机器人回答“我看到了”为依据。文件交付成功与模型能否理解特定格式分别判断。

## 2. 已确认的原因

Issue 的两张截图均出现 `<dsh_im_reply_to>`，其中只有 `attachments: [{ kind: "image" }]`。请求已经进入 Harness，缺口位于引用媒体的准备和传递环节。

在 `src/channels/dingtalk/dingtalk-bridge.mjs` 中：

1. `dingtalkReplyReference()` 会解析引用快照，甚至调用现有解析器得到 `normalized`，但返回时只使用文字及附件类型/名称，未传递其中的图片或文件来源。
2. `dingtalkInboundMessage()` 的 `images`、`files` 只来自当前消息。当前消息是“引用附件后的文字提问”时，这两个数组为空。
3. `promptContentForInboundMessage()` 把引用摘要序列化为文字，只有当前 `images` 中的资源才会进入图片下载链路。
4. 真机还确认：引用富文本中的条目使用 `msgType` / `content`，直接富文本解析使用 `type` / `text`。引用快照入口需要把条目类型转换成现有解析器接受的字段，否则图文消息中的图片不会被识别。

已通过模拟回调跑到真实 Bridge 的 `Harness.ask` 入口验证：

| 输入 | 图片下载次数 | Harness 输入块 |
| --- | --- | --- |
| 群聊引用图片并 @ | 0 | text、text |
| 私聊引用图片 | 0 | text、text |
| 群聊原生图片并 @ | 1 | text、image |
| 私聊原生图片 | 1 | text、image |

普通文件的归一化验证也确认：直接文件有一个 `files` 来源；引用同一文件时只有文件名摘要，`files` 为空。这些是本地模拟验证，不冒充钉钉真机回调验证。

原 [Issue #106 方案](./Issue-106-九渠道引用回复消息公共语义层方案.md) 明确将引用媒体限定为摘要。本次在钉钉渠道补齐实体传递，公共引用文字协议继续沿用。

## 3. 实现方案：在送入模型前补齐附件

### 3.1 保留现有处理顺序

```text
钉钉回调
  → 现有去重、权限、群聊 @ 判断
  → 现有批量输入、命令、审批、提问和会话队列
  → 现有 /help、/status、/new、工作区及 compact 分支
  → 新增：解析本次引用的附件，并入模型输入
  → 现有引用文字、图片 Prompt、来源上下文
  → 现有 askInWorkspaceSession / Harness 文件入站
```

补齐动作放在 `#process()` 的本地命令分支之后、`promptContentForInboundMessage()` 之前。使用单独的 `modelMessage`，保留前面命令和交互判定使用的 `promptMessage`。

原因：直接在入口把引用文件塞入 `promptMessage.files`，会改变 `hasFiles` / `hasImages`，使带引用的 `/new`、`/help` 等命令走向不同分支。引用附件仅在本次消息确实需要进入模型时准备。

### 3.2 复用现有钉钉解析器和延迟下载来源

在 `dingtalk-bridge.mjs` 内增加一个小型引用附件准备函数，不新建附件管理服务：

1. 复用 `text.isReplyMsg`、`text.repliedMsg` 和现有对象/JSON 字符串解析逻辑。必要时仅提取一个共用的引用快照解析函数，避免摘要和实体各自维护字段兼容规则。
2. 只处理直接被引用的那条消息，不递归展开引用链。
3. 对 `picture`、`richText`、`file` 复用现有 `dingtalkInboundMessage()` 的解析结果，保留其 `images[].load` / `files[].load`。
4. 对原生 `audio` / `voice` / `video` 引用，使用相同的文件来源结构及 `api.downloadFile()`；仅补引用侧的类型映射，不改变直接发送这些消息的现有行为。
5. 下载使用当前机器人配置及本次回调的机器人标识。构造现有 `pseudoMessage` 时补齐必要的外层 `robotCode`，不从引用内容切换机器人身份或会话。
6. 保留当前消息已有的媒体及引用摘要，在其后追加引用媒体。多图沿用引用中的顺序；去重仅针对同次请求中明确相同的资源标识，不增加跨消息缓存。

伪代码仅表达接入位置：

```js
// 前面的权限、命令和交互分支保持原样。
const modelMessage = prepareDingtalkReplyAttachments(message, promptMessage, options);
const content = await promptContentForInboundMessage(modelMessage, { signal });
// 后续继续原有来源上下文增强及 askInWorkspaceSession。
// 唯一相应替换：askOptions.files 使用 modelMessage.files。
```

`replyTo` 仍只承载引用文字和摘要；下载码、资源 ID、URL、二进制数据、加载函数不放进引用文字块。新增媒体通过现有顶层 `images` / `files` 传递，无需修改公共引用数据协议。

### 3.3 图片、普通文件分别走已有链路

| 已有机制 | 本次用法 |
| --- | --- |
| `api.downloadImage()` | 按引用资源的下载码取得图片 |
| `promptContentForMessage()` | 继续负责图片格式、单图大小、张数、总大小校验及图片块生成；合并后的当前图片和引用图片一起计入限制 |
| Harness 图片降级 | 模型不支持图片时，继续沿用现有“图片转工作区文件”的降级机制 |
| `api.downloadFile()` | 下载引用的普通文件；文件来源仍为 `{ name, load }` |
| `prefetchInboundFiles()` | 在上述模型输入准备位置预取新增的引用文件，再与已经准备好的当前文件合并；不重建当前文件的下载来源 |
| Harness 文件入站执行器 | 沿用当前 Session 工作区落盘、文件清单注入、保留期和清理逻辑 |
| 现有错误类型及外层 catch | 附件准备或下载失败后，继续通过现有错误回复、状态、Reaction / AI Card 收口 |

现有原生文件在入队时的预取不移动。引用文件先采用命令判定之后的预取，不为提前下载复制命令路由。如果实测证实排队导致引用码失效，再针对该证据处理，不预建另一套队列或下载缓存。

## 4. 下载信息的处理边界

### 4.1 先固定真实回调样本

实施第一步获取群聊、私聊各一份图片引用和文件引用的真实回调，确认 `repliedMsg.content` 实际携带哪些资源字段，并转成脱敏 fixture。

需要记录：消息类型、引用类型、内容是对象还是 JSON 字符串，以及下载码、文件 ID、空间 ID 等字段的存在情况。长期保存的 fixture 使用占位值；不把真实下载码、Token、临时下载地址写入仓库或日志。

这一步由实施者调查，不让用户重新确认功能需求。当前截图证明摘要已进入模型，但未展示原始资源字段；不能假定所有引用回调都带 `downloadCode`。

### 4.2 下载路径

| 回调提供的信息 | 处理方式 |
| --- | --- |
| `downloadCode` / `pictureDownloadCode` | 直接复用现有机器人媒体下载接口，是最小主路径 |
| 可精确定位资源的文件 ID、空间 ID 等 | 若真实样本需要，在现有 `dingtalk-api.mjs` 内补一个小型按 ID 下载适配；继续返回现有文件/图片链路接受的数据 |
| 只有类型、名称或无法精确定位的时间戳 | 明确提示无法取得原附件，请直接重发附件；不按名称或时间猜测其他文件 |
| 下载码失效、资源删除、权限不足 | 使用确定的失败提示；只有存在精确备用资源标识时才尝试上述按 ID 路径 |

钉钉[官方消息示例](https://github.com/open-dingtalk/developerpedia/blob/main/docs/learn/bot/message.md)提供下载码与文件 ID 两种下载说明，但这些是原生消息示例，不能替代引用回调验证。按 ID 路径的实际参数、下载签名及所需权限应通过官方接口与真实样本确定，不从文件名反推资源。

默认复用已有授权。确需按 ID 接口时，列明该接口实际所需权限及缺权错误，不在本修复中重做扫码、自动授权或设置页面。

**完成标准：群聊与私聊的正常图片、正常文件引用都必须有真实成功样本。若某个正常场景拿不到可用资源标识，最小适配尚不足以满足该场景，必须记录未完成项及需要的补充机制；不能把失败提示当作修复完成。** 群文件扫描、历史附件数据库及新缓存都不作为默认实现。

## 5. 失败行为和兼容边界

### 5.1 失败行为

- 已识别出引用附件，却不能获取实体时，复用 `ImagePromptError` / `InboundFileError` 等现有错误出口；仅为“缺少引用资源”增加必要的明确文案及英文翻译。
- 附件下载失败时结束本次处理并提示用户，不把只有附件摘要的请求继续送给模型当作完整输入。多附件任一必要附件失败时统一失败，沿用现有附件链路的整体失败方式，不增加复杂的部分成功状态。
- 对平台可确认的原因给出具体提示；平台未返回细分原因时报告下载失败，不编造“权限不足”或“已过期”。
- 正常纯文字引用，以及卡片引用的本地文字恢复，保留原有行为。

### 5.2 必须回归验证的边界

1. 群聊仍要求现有的 @ 条件；未 @、无权限、重复回调和无有效回复路由的消息，不触发新增附件下载。
2. Session 和工作区仍由当前聊天决定；不去私聊查找群聊附件，也不按引用作者另建会话。
3. `/new`、`/help`、`/status`、`/workspace`、`/compact`、菜单、模型/预设命令、`/stop` / `/steer`、审批和提问的判定保持原样。
4. `/batch` 仍按现有规则处理引用消息，不把引用附件塞进批量输入。
5. 直接发送的图片/文件、原生文件预取、文件保留与清理、图片降级、流式回复及结果文件回传继续走现有路径。
6. 新增下载遵守现有 `signal` 和错误收口，不创建独立重试循环、后台任务或常驻缓存。
7. 修改限定在钉钉入站准备环节；共享输入协议和其他渠道实现不随本次改动调整。

## 9. 实施与验收结果

### 9.1 最终实现

已实现引用快照解析复用、外层机器人标识传递、命令之后的附件合并、同次请求按下载码去重、引用文件预取以及缺少下载码的明确错误。真机发现的富文本 `msgType` 字段差异，仅在引用快照入口归一化，继续复用原来的富文本解析器。

真实回调确认：群聊、私聊引用文件的 `content` 均包含 `downloadCode`、`fileName`、`fileId`、`spaceId`；群聊原生图片引用包含 `downloadCode`；私聊图文引用包含 `richText: [{ msgType: "picture", downloadCode }, { msgType: "text", content }]`。因此直接使用现有下载接口即可，无需增加按 ID 下载接口、权限、依赖、配置或缓存。相关脱敏字段形态已写入 Bridge 测试夹具。

### 9.2 自动化

钉钉 Bridge **104 项通过**；最终 `npm run check` 的 **2,821 项测试、构建、包校验全部通过**。真机富文本字段加入夹具后，先复现群聊和私聊图片下载次数均为 0，再修复至通过。测试核验真实 Bridge 输出的图片字节和文件入站执行器落盘字节，同时覆盖命令、群聊 @、权限、重复回调、当前附件保留、缺少资源及下载失败。

# Issue #199：Telegram 提问实测记录

日期：2026-09-12（Asia/Taipei）

问题：[Telegram bot 无法正常显示 ask_user_question 选项卡片，会卡住](https://github.com/xmanrui/dsh-im/issues/199)。报告版本为 DSH `0.1.5-rc.1`、DSH-IM `4.19.2`。首次排查时未提供触发提示词、工具参数或错误日志；当晚补充截图的分析见下文。

## 结论

21:29 的本机现场确认了故障，现已修复并通过连续两轮真实 Telegram 问答。根因是等待用户回答时，插件仍每 4 秒刷新流式草稿，导致客户端持续处于生成状态、答案无法正常发出，Harness 因收不到答案而一直等待。

修复保持编号文字作答方式：需要用户交互时，停止本轮草稿预览和心跳，等待已发出的草稿请求结束，再用普通消息发送问题。后续进度不再重新激活草稿，最终回复照常发送。代码只增加一个预览停止标记和交互前的调用，没有增加按钮协议、配置项或重试状态机。

首次两组测试确实曾完成问答，但未覆盖持续草稿导致客户端提交受限的状态。此前“未复现”及交互预期差异的分析不足以解释故障；下面保留当时记录，并补充最终定位和验证证据。

## 本机复现与最终修复（2026-09-12 21:29–21:44）

### 故障证据

用户在本机 Telegram 中复现，DSH 停在 `ask_user_question`，发送序号后没有继续。现场会话为 `session-a27ad0f6-1764-49dd-9784-81e2d9df82ed`，seq 75 是 21:29 的提问调用，此后没有成功工具结果；机器人游标保持 `717060295`，没有收到这次等待期间的答案。

截图上方的两条 Blue/Green 来自此前问题被中止后的普通消息回复：对应 turn 4、5，没有成功的问答工具结果，不能用来证明本次交互通过。

根因链路：问题以普通消息发送后，原流式回复的心跳仍继续运行，每 4 秒重新发送“正在使用 ask_user_question…”草稿。客户端因此继续处于生成状态，答案无法送出；插件又在等答案，形成互相等待。

- [Telegram 官方问题记录](https://bugs.telegram.org/c/62189/1)记载了流式草稿活跃时发送按钮被占用、普通消息无法发送的行为，官方回复称这是当前预期行为。
- [Telegram 草稿协议](https://core.telegram.org/api/bots/ai)说明，收到同一会话的普通消息时应清除流式草稿。问题消息本身可以清除草稿，但后续心跳和迟到的进度会再次激活它。

诊断过程中短暂停住进程以观察草稿过期，随后恢复。该操作触发了连接重试，原问题返回 `ASK_CANCELLED`，排队的序号随后作为普通消息送达。这次实验受连接重试干扰，不能作为问答成功证据；修复后的验证使用了新会话，没有依赖这次取消。

### 最小修复

- `TelegramDeliveryStream.stopPreview()` 立即禁止后续草稿更新，并等待已在发送的草稿结束，防止它晚于问题消息到达。
- 接到用户交互请求时，共享桥接层对这类草稿流停止心跳并等待 `stopPreview()`，随后按原流程发送问题或审批文字。
- 本轮后续只保留最终回复，下一轮重新创建正常的流式回复。普通群聊占位消息不受此逻辑影响。
- 已重建 `lib/index.js` 并加载到本机原 DSH `0.1.5-rc.2` 服务，地址仍为 `127.0.0.1:3080`。基线插件版本为 `4.20.1`，未发布新版本。

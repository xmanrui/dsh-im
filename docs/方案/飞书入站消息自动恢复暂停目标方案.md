# 飞书入站消息自动恢复暂停目标方案

日期：2026-10-31。实施基线：`main` 的 `4f1e425` + `#500`（`2b4a1b9`），包版本 `5.8.0`。分支：`feat/feishu-goal-autoresume`。

目标只是「贴一条消息就能让目标继续跑」。但目标在 IM 里并非只有一种「停」：

- 人工在 Web 端点「暂停」→ `phase: "paused"`（durable，写入 `goal/change`）；
- Host 重启（或 session 恢复正常化）→ 目标仍是 `phase: "active"`，但 `activation` 掉成 `"disarmed"`。`activation` 是**进程内存态、永不持久化**（`dsh-goal` 的 typert schema 原文：*Process-local continuation eligibility; never persisted.*），`dsh-goal` 在 `agent/created` 时把每个 agent 置为 `disarmed`。

两种状态在产品 UI 里显示成同一句「已暂停的目标」（`dsh-client-ui-goal/lib/client.js:526-527`），而 IM 侧此前没有任何入口能把它们唤醒：`#accept()` → `#answerWithStepPush()` 只负责一轮问答，没有任何代码调用 `goals/resume`。用户发「继续」只会得到一轮普通对话，目标仍停在原地——这正是本方案要修的行为。

## 判定

收到一条会进入模型的入站消息、且该对话已绑定会话（`state.sessionFor(key)` 有值）时，先读该会话的 Goal：

| Goal 状态 | 行为 |
| --- | --- |
| `phase: "active"` 且 `activation: "disarmed"` | 调 `goals/resume` 恢复，本轮开始前完成（Host 重启遗留的「已暂停」，用户并没有主动暂停）。 |
| `phase: "paused"` | 默认不动；渠道显式配置 `goalAutoResume: 'all'` 时与上一行相同。人工暂停是明确意图，不能被任意一句话推翻。 |
| `phase: "active"` 且 `activation: "armed"` | 不动。目标轮已在跑，`#500` 的过程卡负责可见性。 |
| `phase: "blocked"` / `"complete"` / 无 Goal | 不动。blocked 需要人工处理阻塞原因，完成的目标不应重新开跑。 |

不为「继续」这类措辞做匹配：能走到这一步的已经是一条真人消息，措辞判断只会让「接着说点什么」变得不可预测。

只认真人：同一桥接里机器人也能通过访问检查（群聊里 @ 本 bot 即可进入问答），自动化消息不携带恢复意图，因此 `#resumeParkedGoal()` 要求 `event.sender.sender_type === 'user'`。

## 边界与取舍

- **默认只恢复「未武装」**。重启遗留的 disarmed 不是用户的决定，消息到了就该继续；人工 `phase: "paused"` 是明确意图（用户可能正要说「先别继续，讲下进度」），默认保留，只有 `goalAutoResume: 'all'` 时一起恢复。`blocked` 说明有明确阻塞原因，自动恢复等于绕过阻塞；`complete` 已完成，重新 resume 会凭空再开一轮。
- **先恢复再问模型**。恢复发生在 `#preparePrompt()`/`#ask()` 之前，所以本轮结束时 goal driver 能立刻接下一轮；用户不需要发两次消息。
- **只有确认恢复成功才算成功**。`goals/resume` 若因服务不可用返回 `undefined`，适配器返回 `{ resumed: false }`，桥不提示「已恢复」——不能对用户宣称一个没有发生的状态变化。
- **revision 竞争只重试一次**。读取与恢复之间可能被 goal driver 或 Web 端推进；重试前重新读一次，只有目标仍处于可恢复状态且 revision 变化时才重发。否则放弃并记录，不阻塞本轮。
- **老 Host 自动降级**。宿主没有 `goals/*` 端点（旧版 DSH 或关闭 goal 服务）时，`gateway/definition-unavailable` / `service-unavailable` 会让适配器把自己关掉，只记一条 debug，不会每条消息失败一次。
- **不做按钮、不做多轮编排**。卡片按钮与「帮我把目标改个措辞」属于另一个 PR 的范围；本方案只解决「消息到了，目标却没醒」。
- **渠道范围**：只改飞书。个人微信 / 企业微信等通道的目标可见性与恢复能力另行处理。

## 验证

`test/goal-control.test.mjs`（7 项）覆盖适配器：人工暂停默认不恢复、`resumePaused` 开启后恢复、active+disarmed 恢复、armed/blocked/complete/无目标不恢复、revision 竞争重试一次、resume 不可用不算成功、无端点自动关闭。

`test/channels/feishu/goal-resume.test.mjs`（7 项）覆盖桥：入站消息恢复并提示、非暂停目标不提示、过程卡首块为恢复提示、机器人消息不恢复、未绑定会话不查询、恢复抛错仍正常回话、未注入 `goalControl` 时行为不变。

在旧代码（`2b4a1b9`）上移除 `bridge.mjs` 的钩子后，4 项用例失败、2 项「不该发生任何事」的守卫用例仍然通过，说明用例确实在验证新行为。

真机验证：重启 Host（重建进程内存态）→ 在绑定话题里发一句「继续」→ 观察卡片首行出现「🔄 目标已恢复自动续跑」，且本轮结束后 goal driver 自动接下一轮。

# Issue #339：会话双向同步 11 渠道 Markdown 渲染方案

日期：2026-10-11（Asia/Taipei）。

关联 Issue：[会话同步镜像到 IM 的回答希望走 Markdown 渲染](https://github.com/xmanrui/dsh-im/issues/339)。

状态：方案已实施；自动化检查通过。实际客户端验证及边界说明见第 11 节。

分析基线：项目 `4.38.0`，提交 `bbafc99`。第 1–10 节保留设计依据和验收范围；第 11 节记录后续实施及实际验证结果。

## 1. 问题与目标

Session Sync 将 DSH Web／CLI 的最终助手回答镜像到 IM。当前部分渠道的普通聊天回复能够渲染 Markdown，但同步回答经过纯文本主动发送路径，标题、粗体、表格、代码和链接等语法原样显示。

方案采用“同步链路透传格式，各渠道复用现有发送能力，少量补齐缺口”。覆盖所有当前支持会话双向同步的 11 个渠道，各渠道的呈现效果按其现有能力确定。

核心目标：

- 有现成 Markdown 或富文本能力的渠道，同步回答接入这些能力。
- 需要不同格式语法的渠道做有限适配；纯文本渠道完整保留内容。
- 发送失败或结果未知不能被误报为成功。
- 格式回退不能造成已发送内容整条重发。
- 尽量复用现有代码、错误识别、分段、会话绑定和测试机制。

## 2. 范围与边界

覆盖渠道：飞书、Telegram、QQ、钉钉、Slack、企业微信机器人、Matrix、Discord、WhatsApp、企业微信应用、微信。

沿用现有会话同步范围：

- 当前 Host、已开启同步的私聊目标。
- DSH Web／CLI 成功完成后的最终助手回答。
- 定时任务成功完成后的最终助手回答。
- 用户输入继续走普通文本；平台客户端原生解释部分符号的行为保持现状。
- 会话绑定、目标选择、同步时机、权限和审批机制沿用现有实现。

本次不扩展群聊、Topic、Thread、显式远程 Harness、附件同步或新的同步入口。共享发送代码已有群聊或线程调用的，需要回归其行为，但不因此开放新的会话同步范围。

邮箱、iMessage 虽有消息收发能力，但目前没有接入这项会话双向同步功能；它们及 AI Office 不在本方案内。

不新增配置项、统一渲染框架、队列、后台重试系统、存储版本或完整 Markdown 解析器。无需为其余渠道逐一注册新的 Session Sync 镜像渲染器。

### 2.1 难度判断

整体属于中等工作量，主要成本在渠道差异和回归验证，公共格式透传本身较简单。

- 低难度：公共参数透传、Telegram 复用富文本发送，以及已有渲染或文本渠道的兼容性确认。
- 中等难度：QQ 部分发送失败的结果处理，钉钉和 Slack 的主动消息格式接入，代码围栏跨分段的完整性。
- 最容易扩大范围：WhatsApp 的语法转换。严格限定常用格式，不追求完整 Markdown 兼容；复杂内容保留原文。

不需要改会话同步架构，也不需要新依赖。实施前的主要不确定项是钉钉主动消息接口限制、Slack 应用是否接受 Markdown block，以及各平台客户端最终显示效果；通过针对性接口验证和客户端冒烟测试确认。

### 3.1 飞书：保留已有完整路径

飞书已经注册 Session Sync 专用镜像渲染器。只有渲染器确认完整最终回答可见，协调器才抑制后续正文兜底；挂起中的卡片不是送达证明。

本次保留这套机制。镜像失败后的文本兜底仍为 `plain`，避免“镜像卡片失败后，再发一张 Markdown 卡片”的重复尝试。

飞书现有主动 Markdown API 已有“平台拒绝或网络结果不确定时，不自动改发纯文本”的测试约定。保持该约定，不借本次改动重新设计卡片恢复或主动发送行为。

### 3.2 QQ：完整发送结果必须可见

现有 `sendMarkdownReply` 在部分分段成功后遇到错误，可能结束发送并返回已有结果。如果直接复用，同步层可能误判整条回答已经送达。

建议仅增加一个可选的“要求完整发送”参数，由同步调用启用；后续分段失败时向上报告。普通聊天已有的部分回复提示保持原样。

Markdown 拒绝识别继续复用现有已知错误规则，不把任意异常或任意 HTTP 4xx 都当成可回退条件。

### 3.3 Slack：使用标准 Markdown block

标准 Markdown block 与现有 `mrkdwn` 不是同一种格式。不能只把普通消息的 `mrkdwn` 打开，就认为标准 Markdown 已经正确渲染。

根据 [Slack 官方文档](https://docs.slack.dev/reference/block-kit/blocks/markdown-block/)，单条请求中的 Markdown blocks 累计上限为 12,000 字符。因此新增发送路径需要自己的长度限制，不能直接套用当前普通文本限制。

继续保留顶层 `text`，并复用现有输出文本处理及 mention 防护。若平台明确拒绝 Markdown block，当前失败分段退回已有文本发送。

官方文档将该 block 放在平台 AI 功能的使用场景中。本方案不假设所有现有应用均可使用：需验证当前应用的实际支持情况，并覆盖不支持时的明确拒绝回退；不为此引入新的流式发送或应用权限配置流程。

### 3.4 WhatsApp：有限格式转换

根据 [WhatsApp 格式说明](https://faq.whatsapp.com/539178204879377/?cms_platform=web&locale=en_US)，其格式语法与标准 Markdown 存在差异。

本次只适配以下常用内容：

- 标题转换为加粗文字。
- 常见粗体、斜体、删除线转换为平台对应语法。
- 链接保留“标题＋URL”，不能丢失链接目标。
- 代码保留原始内容，适配等宽格式；不能改写代码中的星号、下划线等字符。
- 表格、复杂嵌套和其他不确定语法保留原文。

转换限定在渠道内部的一个小型函数。转换在发送前完成，再按最终内容长度分段；失败时直接使用原文，不增加网络重试。

### 3.5 企业微信应用与微信：明确文本降级

企业微信应用当前承担企业微信客户端和微信插件入口，本方案选择现有文本发送作为兼容基线，不在无法确认接收客户端时统一切换消息类型。这是本次实现范围的选择，不意味着所有客户端都没有富文本能力。

微信同样沿用现有文本协议及上下文处理；主动发送补齐现有 1,800 UTF-16 单元分段，Markdown 使用共享分段工具保护跨消息代码围栏。两者都应保留完整正文、代码和链接，不为去除 Markdown 符号引入另一套有损转换。实际微信客户端可能自行渲染 Markdown，但不把这种客户端表现声明为协议保证。

## 4. 公共链路的最小改动

### 4.1 同步协调器表达格式

在 `plugin-src/host/session-sync-coordinator.mjs` 的发送方法中增加 `format` 参数：

- 用户输入为 `plain`。
- 助手回答为 `markdown`。
- 飞书镜像失败后的兜底保留 `plain`，用一处明确的例外维持现有行为。
- 助手前缀与正文之间增加空行，避免影响首段 Markdown。

继续复用已有目标去重、每会话顺序处理、多目标失败隔离和完成状态检查。

### 4.2 沿现有 options 透传

`plugin-src/host/delivery-service.mjs` 的 `sendSessionSyncText` 接收并校验 `plain | markdown`，再继续传递。

`plugin-src/host/delivery-adapter.mjs` 已经透传 options，不需要新增发送接口。省略格式时仍为 `plain`，连接测试和其他现有调用维持默认行为。

### 4.3 共享桥接层复用发送入口

`src/channels/shared/text-harness-bridge.mjs` 的 `sendProactiveText`：

- 格式为 Markdown，且渠道提供 `sendDelivery`，则使用 `createTextDeliveryBlock(text, 'markdown')` 调用它。
- 其他情况继续 `sendText`。

独立实现主动发送的渠道，在各自现有方法中处理格式。新增能力也可能被正常回复路径复用，因此需要回归普通聊天行为。

### 4.4 检查已有发送结果

当前同步适配层只要渠道调用不抛异常，就返回成功；部分富文本发送器却通过返回值表达失败或结果未知。

同步适配层需要识别已有的失败值及 `deliveryOutcome: 'failed' | 'unknown'`，并使用项目已有错误类型向上报告。继续兼容旧渠道的正常返回方式，不要求所有渠道迁移到一套新回执结构。

这项检查首先限定于同步发送入口，不顺带重构整个主动投递 API。

## 5. 失败回退与日志

回退放在各渠道发送处，协调器不负责重发。以下规则约束本次接入的发送路径；飞书继续保留已有镜像卡片的确认与兜底机制。

| 情况 | 处理原则 |
| --- | --- |
| 发请求前，本地渲染或转换失败 | 有文本发送能力的渠道直接发送原文 |
| 平台明确拒绝 Markdown 格式 | 有安全回退路径时，仅当前失败分段回退一次 |
| 权限不足、目标失效、鉴权失败 | 报告失败；换格式通常无法解决 |
| 超时、连接中断、结果未知 | 不新增自动重发 |
| 前几段已成功，后续失败 | 保留已发送部分，不重新发送整条回答 |
| 文本回退也失败 | 向同步层报告失败，由现有日志记录 |

复用已有平台错误分类；新增回退只匹配可确认的格式拒绝，不使用“捕获所有错误后改发文本”的通用逻辑。

日志只补必要信息：渠道、阶段、错误类别、是否发生格式降级。Telegram 当前静默的本地渲染失败增加一条警告，不记录回答正文、凭据或完整平台请求。

## 6. 长消息处理

- Telegram 继续使用自身富文本分段。
- QQ 继续使用现有 Markdown 分段。
- 企业微信应用继续使用按 UTF-8 字节分段。
- Slack、钉钉、Discord、WhatsApp 如需保护代码围栏，优先提取 QQ 已有的纯分段函数，保留原有测试，不改 QQ 的发送流程。
- Matrix 继续复用现有文本／HTML 构造及分段路径，验证长代码与正文完整性。

最多提取一个纯分段工具，负责切分文本及必要的结构保护，不承担发送、重试或渠道能力管理。各渠道保留自己的长度参数。

WhatsApp 先转换，再按最终内容长度分段。Markdown 分段产生的补齐围栏等辅助内容，不能在文本回退时造成正文重复或丢失。

## 7. 验证计划

### 7.1 公共同步行为

在现有 `test/session-sync-coordinator.test.mjs`、`test/delivery-service.test.mjs`、`test/delivery-adapter.test.mjs` 和共享桥接层测试中补齐：

- 11 个渠道均能把格式参数传到正确发送入口，绑定与目标校验仍然生效。
- Web／CLI 输入使用普通文本，最终助手回答使用对应渠道策略。
- 定时任务只同步最终回答，不发送内部提示词。
- IM 发起的任务不重复同步；失败、中止的任务不发送成功回答。
- `/new`、切换 Session、关闭同步或修改目标后，旧回答不会误投。
- 一个渠道失败不阻塞其他渠道，也不阻塞下一轮。
- 发送失败或结果未知不会被报告为成功。
- 非法格式在发送前拒绝；发送前取消不产生平台请求。
- 没有格式参数的旧调用、连接测试、审批提醒及正常聊天回复不发生意外变化。

### 7.4 实际客户端验证

发布前对 11 个渠道逐一进行已开启同步的私聊冒烟验证：

- 一次包含常见 Markdown 的短回答。
- 一次需要分段的长回答，包含代码和链接。

### 11.2 验证中发现并修复的问题

1. **WhatsApp 代码中含三反引号时，转换可能破坏边界。** 对无法安全表示的块保留原文；增加代码、复杂嵌套、表格、转义和链接保护测试。
2. **飞书长代码跨镜像卡片后丢失格式。** 真实机器人第一次 400 行验收中，第二张卡片从 `ROW_0214` 起显示为普通段落，结束标记反而进入了代码块。原因是原按字节分段没有给后续独立 Markdown 元素补代码围栏。现在复用共享分段工具，并保留卡片字节预算与原有镜像确认、文本兜底机制。新增真实镜像链路回归：跨卡片各段有完整围栏，400 行顺序、缩进、中文、emoji 均保留，末尾可见且不重复发正文。该测试修复前失败，修复后通过。
3. **Telegram 长代码显示省略的核对。** 对指定机器人增加一次确定性 400 行发送，保存真实 API 回执。两段代码分别 389 行、11 行，服务器返回代码正文与请求逐字符一致，400 行无缺漏、无重复。客户端显示省略不能当作发送丢失，因此没有因此改写发送机制。

4. **微信主动同步遗漏已有长度分段。** 首次实测一次提交 30,466 UTF-16 单元，未使用普通回复已有的 1,800 字符预算。补齐主动路径分段：普通文本复用 `splitWeixinText`，Markdown 复用共享分段工具；逐段沿用 `sendTrackedText`、上下文缓存和发送记录。新增回归先失败后通过，覆盖 400 行代码无丢失/重复、围栏、长度、中文/emoji、逐段记录、明确拒绝、未知网络结果和取消。诊断同时保留完整正文长度及实际失败段序号，不把第 N 段误记为单段发送。未新增重试、队列或额度管理。

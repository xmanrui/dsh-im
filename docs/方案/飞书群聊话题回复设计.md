# 飞书群聊「以话题方式回复」开关设计

日期：2026-09-04
范围：飞书（含 Lark）渠道
目标版本：v4.x（下一个 Minor 版本，未定）

## 1. 背景与目标

飞书普通群中，机器人现在对每条被响应消息做「平铺回复」：回复落在群主时间线，且整群主时间线的问答共享一个 Harness Session（`group:<chat_id>`）。群成员之间的提问混在同一条时间线上，dsh 侧也无法区分“这是哪一问的上下文”。

目标：为**每个飞书机器人**增加一个开关「群聊以话题方式回复」。开启后：

1. 群聊主时间线里**明确向机器人提问**（被 @ 等）的消息，机器人用飞书「话题」方式回复：飞书自动围绕该提问开启一条独立话题，整段问答落在话题内，群主时间线不被连续问答刷屏；
2. 每个飞书话题对应 dsh 会话列表里的一条**独立会话**，上下文/历史互不串；
3. 话题内的后续追问保持在原话题、原 dsh 会话中。

非目标：

- 不改私聊（p2p 无话题分组，维持现有连续会话）；
- 不做跨渠道迁移，其他渠道语义不变；
- 不改「回复链用于待处理问题关联」的既有交互归属逻辑。

## 2. 平台能力依据（飞书开放平台）

依据飞书[「话题概述」](https://open.feishu.cn/document/im-v1/message/thread-introduction) 及本项目锁定的 `@larksuiteoapi/node-sdk@1.73.0`：

- 普通群对一条**非话题**消息调用**回复消息接口**并传 `reply_in_thread: true`，飞书会**自动创建一条新话题**并把回复放进话题；对**话题内**锚点消息同样设置则保持在原话题。
- 回复接口的响应会返回该话题的 `thread_id`（`omt_` 开头，租户内唯一）；入站事件中，话题内消息携带 `thread_id`。
- **不能**用发送消息接口 + `receive_id_type=thread_id` 往话题发新消息（会报 `99992402`）；向已存在话题追加消息只能对**话题内某条消息**走回复接口。
- SDK `im.v1.message.reply` 的 `data` 已支持 `reply_in_thread?: boolean`，响应含 `message_id` / `root_id` / `parent_id` / `thread_id`，无需升级依赖。

## 3. 决策记录

| 问题 | 决定 |
| --- | --- |
| 开关位置 | 每个机器人各自开关，置于机器人卡片「群聊响应方式」旁 |
| 生效范围 | 仅群聊；私聊维持现状 |
| 会话历史 | 开启后主时间线每个新提问=全新独立会话，不继承开启前群共享会话历史 |
| 何时自动开话题 | 仅当消息**被 @/明确提问**（`#isAddressed`）时才开新话题；群响应模式=全部时对非 @ 闲聊的回复仍保持平铺旧行为 |
| 开话题回复失败 | 回落到普通群消息发送（沿用现有 reply→create fallback），保证用户看到答复 |

## 4. 现状梳理

### 4.1 发送路径

所有用户问答产生的文字/交互卡片/文件消息最终汇聚到少数底层原语，全部以是否存在 `replyTo` 决定回复还是平发：

- `bridge.mjs #send(chatId, text, { replyTo })`（`src/channels/feishu/bridge.mjs:4004`）：文字原语；reply 失败回落到 `message.create`（`4016-4024`）。
- `bridge.mjs #sendCard(chatId, cardJson, { updateMessageId, replyTo })`（`bridge.mjs:2358`）：交互卡片原语；reply 失败回落到 `message.create`（`2396-2403`）。
- `feishu-channel.mjs #sendCard(chatId, cardId, replyTo)`（`feishu-channel.mjs:458`）：CardKit 流式卡片。
- `feishu-channel.mjs #sendArtifact(chatId, file, { replyTo })`（`feishu-channel.mjs:293`）：文件/图片产物。

仓库当前**从未**在任何 `reply` 调用里设置 `reply_in_thread`。

### 4.2 会话隔离

`conversationKey`（`src/channels/feishu/message-utils.mjs:16-31`）：

- p2p → `p2p:<sender_id>`；
- 群消息带 `thread_id` → `group:<chat_id>:thread:<thread_id>`（每话题独立 key）；
- 群消息无 `thread_id`（主时间线）→ `group:<chat_id>`（整群共享）。

每个 conversation key 在 `state.sessions[key]`（`src/channels/feishu/state-store.mjs:51-56`）持久映射到一条 Harness session，因此新 key 自然就是 dsh 会话列表里的一条独立会话。

### 4.3 设置链路（参照 groupResponseMode）

新增布尔字段需走通整条链路（见 `plugin-src/host/channels/feishu/` 与 `src/channels/feishu/`）：

1. `plugin-config-store.mjs normalizeBot` 增加字段与默认值；
2. `multi-bot-controller.mjs`：`configuredBotFingerprint`、新增 update 方法（持久化 + push live + status 投影）、`#startRuntime`/`production.mjs` 构造映射；
3. `feishu-runtime.mjs`：字段 + `setXxx` 转发到 bridge；
4. `bridge.mjs`：字段 + `setXxx` + 运行时读取；
5. host RPC `rpc.mjs`：校验 + 分发 + endpoint 常量；`plugin-src/client/channels/feishu/api.js` normalizer；
6. 客户端 UI `index.js`：在 `GroupResponseModeEditor` 后加开关组件与 save 回调；
7. `plugin-src/client/i18n.js`：EN 词条（zh 由 identity 自动推导）。

## 5. 设计

### 5.1 设置项

- 字段名（暂定）：`groupTopicReply`（bool，默认 `false`；`value === true` 归一，同 `groupMessagePermissionGranted`）。
- 标签：`群聊以话题方式回复` / `Reply to group chats as Feishu topics`。
- 帮助文案要点：主时间线向机器人提问会开启独立话题、回复落在话题内、每个话题=dsh 独立会话互不串记忆、私聊不受影响。
- UI：复刻 `GroupResponseModeEditor` 的 autosave 形态，用 switch（参考 `plugin-src/client/context-enhancement.js:120-126` 的 checkbox+role=switch）。

### 5.2 运行时行为

引入状态（bridge 实例内，跟随每个 bot）：

- `#groupTopicReply: boolean`（启动从 per-bot 配置读入，运行时通过 `setGroupTopicReply(v)` 更新，语义同 `#groupResponseMode`）；
- `#groupChatIds: Set<chat_id>`：记录本 bot 见过的群聊 chat_id（供发送原语判断“是否群聊”）。
- 话题注册表 `threadTopics: Map<thread_id, rootMessageId>`（持久化到 state store，字段暂定 `topics`）：本 bot 自动开的话题。

#### 5.2.1 入站 key 解析（群聊且开关开）

`conversationKey` 的判定从纯函数迁到 bridge 内 `#conversationKey(event)`：

- p2p：不变 `p2p:<sender>`；
- 群消息带 `thread_id`：
  - 注册表命中 → `group:<chat>:managed:<rootMessageId>`（本 bot 自动开的话题，沿用最初提问的会话）；
  - 未命中（既有话题/话题群）→ 沿用 `group:<chat>:thread:<thread_id>`；
- 群消息无 `thread_id`（主时间线）：
  - 被 @/明确提问（`#isAddressed`，与现有接受门槛一致）→ `group:<chat>:managed:<message_id>`（全新会话，不继承 `group:<chat>` 历史）；
  - 未提问（仅群响应模式=全部时才可能走到）→ 沿用 `group:<chat>`（平铺旧行为）。

会话键迁移只在“首次开启时”发生一次语义变化：开关开启后的主时间线提问不再落入旧的 `group:<chat>`。旧 `group:<chat>` 会话保留但不再被主时间线新提问使用；不做历史复制（决策见 §3）。

#### 5.2.2 发送：自动开话题

底层原语新增选项 `replyInThread`，**仅**当以下全部成立时置 `true`：

- `#groupTopicReply === true`；
- 目标 chat 在 `#groupChatIds`（确认是群聊）；
- 本次是 reply 分支（存在 `replyTo`），且锚点消息需要话题化（见下）。

发送时给 `im.v1.message.reply` 的 `data` 补 `reply_in_thread: true`。锚点维持现状（触发消息 `message_id` / 卡片消息 id / watch 记录锚点），话题内每条回复都以“话题内最近相关消息”为锚，配合 `reply_in_thread: true` 使整串留在同一话题。

首次对主时间线提问做话题化回复后，从响应取 `thread_id`，登记 `threadTopics[thread_id] = <根消息 id>` 并持久化。之后该话题内入站消息即可经注册表解析回 `group:<chat>:managed:<rootMessageId>` 会话。

##### 谁需要话题化

- **主时间线 + 被 @/提问**：开新话题（需要 `reply_in_thread: true`），并把 `threadTopics` 登记。
- **已在话题内的消息**（注册表命中或既有话题）：回复到该消息即留在原话题；`reply_in_thread: true` 保证归位。
- **主时间线 + 未被 @（仅 all 模式）**：平铺回复，不开话题、不设 `reply_in_thread`，回落既有 `group:<chat>` 会话。
- p2p：永不设置 `reply_in_thread`。

##### 降级

`#send`/`#sendCard` 现有 reply→`message.create` 的 fallback 保留：`reply_in_thread` 回复失败（消息已删、群不支持等）→ 普通群消息发送并告警（决策见 §3）。

##### 需要传递 `replyInThread` 的调用面

由勘察得出，发送原语集中注入最稳妥，中间层（约 40 处 replyTo 透传点）无需逐一改：

- `bridge.mjs #send`、`#sendCard` 在 reply 分支加 `reply_in_thread`；
- `feishu-channel.mjs #sendCard`（流式卡片）、`#sendArtifact`（文件/图片）同样处理；
- 各调用点仅在“是否群聊+开关开+话题化条件”为真的路径上由原语自行推导，避免为每个 replyTo 调用点引入布尔。

### 5.3 命令、菜单、审批与 Watch 投递

- 卡片按钮、`/sessionlist`、`/m` 等仍锚在各自触发消息/卡片消息上；话题内触发的命令其回复随锚点留在话题。
- `/watch` 完成推送沿用现有 `replyToMessageId` 锚点机制（该锚点是话题内消息时，回复即在话题内），并带 `reply_in_thread: true`。
- 审批/提问交互的 `replyToMessageId` 同理。

## 7. 风险与开放项

- **话题支持度差异**：普通群/话题形式群/老群对 `reply_in_thread` 的反馈可能不同；真机闭环前以回复接口返回码为准，fallback 保底。
- **`thread_id` 归属确认**：自动开话题的回复响应返回 `thread_id` 已在官方文档写明；真机仍须验证主时间线根消息的“无 thread_id”与话题内后续消息“带 thread_id”的入站形态。
- **开关切换时的会话边界**：开关打开后旧 `group:<chat>` 会话不再承接主时间线新提问；如用户期望平滑迁移需另行设计，本期不做。
- **话题数量**：all 模式下仅被 @/提问开话题，已避免话题刷屏；仍需监控话题上限。
- **跨机器人与重启**：注册表随 per-bot state store 持久化；重启后自动话题的会话归属可恢复。若注册表丢失，话题消息会退化为 `group:<chat>:thread:<thread_id>` 的新会话（隔离仍在，仅该话题原会话历史不再续接）。

## 8. 验收要点（草稿）

1. 某飞书机器人开启开关后：群主时间线 @ 提问 → 飞书出现独立话题、回复落在话题内；dsh 会话列表出现该话题对应新会话。
2. 在话题内追问 → 回复仍在同一话题、dsh 侧仍是同一会话（记忆延续）。
3. 私聊行为与开关无关，前后一致。
4. 开关关闭 → 完全回到现状（主时间线平铺回复 + `group:<chat>` 共享会话）。
5. all 模式下非 @ 闲聊：不开话题、平铺回复；@ 提问：开话题。
6. 话题回复失败回落普通消息，不丢答复。
7. 权限扫描/既有回归测试全绿。

# 会话超时

[English](session-timeout.en.md) | 中文

会话超时让 IM 渠道在某个对话**空闲过久**后，自动解绑该对话对当前 Session 的绑定；下一条消息进来时不再沿用旧 Session，而是自动开一个全新 Session（新上下文）。这相当于在用户离开太久时让对话"重新开始"，避免机器人把新问题带回到一个早已过时的上下文中。

本功能**默认关闭**；未开启时插件的行为与开启前完全一致。

> 本功能**只解绑绑定，不删除 Session 日志**。被超时解绑的旧 Session 的持久化日志按 Harness 的不可变性约定保留，`/history` 命令仍可回到那个旧 Session 继续对话。

## 一、什么是"清理上下文"

"清理上下文"= 解绑 `conversationKey → sessionId`：调用 `ConversationStateStore.clearSession(key)`，删除该对话对当前 Session 的绑定记录。下一条 IM 消息进来时，由于 `sessionFor(key)` 返回 null，dsh-im 既有路径会自动走 `createSession`，产生新 `sessionId` 并写回绑定。这是 dsh-im 已经具备的隐式行为，**不需要新增任何创建分支**。

- 旧的 Session 不销毁、不删除。
- 旧的持久化日志、Session 记录按 Harness 不可变性约定保留。
- `/history` 仍能找回那个旧 Session 继续对话。

可选的临时文件清理（`inbound`/`directory` 两档）是与"清理上下文"**正交、可选**的附加动作，由 `cleanupScope` 配置控制，下文 §四 详述。

## 二、配置文件位置

会话超时的配置分散在三处，本节说明各自的位置与作用。按既有 inbound-ttl 的分层方式，新增内容**不引入新的配置文件**。

### 2.1 运行时配置：`$DSH_HOME/integrations/dsh-im/settings.json`

**作用**：持久化会话超时的运行时配置（与 `inboundAttachmentTtlHours` 共用同一份文件）。

**位置**：`~/.dsh/integrations/dsh-im/settings.json`（Windows 上是 `%USERPROFILE%\.dsh\integrations\dsh-im\settings.json`）。这里的 `~` 即 `$DSH_HOME`；若未设环境变量，则回落到用户主目录下的 `.dsh`。

**示例**：

```json
{
  "version": 1,
  "inboundAttachmentTtlHours": 168,
  "sessionTimeout": {
    "enabled": true,
    "timeoutMinutes": 30,
    "scanIntervalMs": 300000,
    "cleanupScope": "none",
    "notify": true,
    "notifyText": "会话超时，已开启新会话；如需继续上一段，请使用 /history"
  }
}
```

| 字段 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `enabled` | `boolean` | `false` | 总开关。`false` 时一切 touch/扫描都不做 |
| `timeoutMinutes` | `number` | `30` | 空闲超时阈值，单位分钟，范围 1–10080（7 天） |
| `scanIntervalMs` | `number` | `300000`（5 分钟） | 扫描间隔，单位毫秒，范围 60000–3600000 |
| `cleanupScope` | `"none"\|"inbound"\|"directory"` | `"none"` | 文件清理范围（详见 §四） |
| `notify` | `boolean` | `true` | 是否在解绑前发提示消息 |
| `notifyText` | `string` | 见示例 | 提示文案（中英 i18n 字典可覆盖） |

**文档版本与兼容性**：`sessionTimeout` 子对象与 inbound-ttl 共用 `version: 1`，**不新增版本号**。旧文件缺该子对象时按默认值兜底（`enabled: false`），不会被读坏；损坏或未来版本回落到「**禁用** + 默认阈值」，避免不可读的意图扩大为会话解绑——这与 inbound-ttl「损坏 → keep-forever」的兜底方向一致。

**写入时机**：只有 RPC `set`（含启动期写入 host 默认值）会写盘；`touch` 与扫描周期**均不写盘**。

**活动记录不落盘**：每个对话的 `lastActivityAt` / `runningSince` / `sessionId` 只存在于内存 Map 中，不会写进 `settings.json`。原因是 touch 发生在每条入站消息与每个回合结束时，落盘会造成高频全文件重写，也会把大量平台标识（chat_id / open_id）固化进用户的配置文件。代价是**重启后空闲窗口重新计时**：会话需要再空闲满一个阈值才会被清理，见 §5.4。

早期版本曾把 `sessionActivity` 子对象写在同一份文件里。当前版本读取时会**忽略**它，并在下一次 `set` 写盘时顺手删除该残留子对象。

### 2.1.1 打开 DSH 诊断日志

dsh-im 使用 DSH/Cordis 的 logger。若要观察超时是否加载、是否启动扫描、每次消息是否 touch，以及扫描为何跳过某个会话，需要在实际运行的 profile 的 `cordis.yml` 中加载 console exporter：

```yaml
- id: logger-console
  name: '@deepseek-ai/cordis-plugin-logger-console'
  config:
    showDiff: true
    levels:
      default: 2
      dsh-im: 3
      dsh-im:session-timeout: 3
      dsh-im:file-ingress: 3
      dsh-feishu: 3
```

日志等级为 `0=error`、`1=info`、`2=warn`、`3=debug`。dsh-im 的关键日志默认不会写入仓库目录；console exporter 输出到 Host 的 stdout/stderr，可在 PowerShell 中保存：`pnpm dsh --profile <profile> "task" *> dsh-im-debug.log`。

超时诊断会记录 settings 路径、最终 `enabled`、阈值、扫描间隔、tracked 数量、touch、运行中保护、首轮扫描 grace 和过期数量。飞书文件诊断会记录 message/file 的短标识、下载阶段、错误码、最终 Session workspace、staging 目录和文件数量，不记录文件内容。

### 2.2 Host config（cordis.yml 注入）

**作用**：Host 启动时 cordis 注入的 `config` 对象，决定是否在启动期启用本功能及启动期默认值。如果你不用 cordis.yml 而是 `config.json`，对应字段直接放到顶层即可。

**示例（cordis.yml 片段）**：

```yaml
config:
  sessionTimeoutEnabled: true
  sessionTimeoutMinutes: 60
  sessionTimeoutCleanupScope: inbound
  sessionTimeoutReplyTimeoutMs: 900000
```

| 字段 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `sessionTimeoutEnabled` | `boolean` | `false` | Host 启动期硬开关。如果显式 `false`，运行时 store 中的 `enabled` 也不生效 |
| `sessionTimeoutMinutes` | `number` | `30` | 启动期默认阈值，store 有覆盖时以 store 为准 |
| `sessionTimeoutCleanupScope` | `"none"\|"inbound"\|"directory"` | `"none"` | 启动期默认档位 |
| `sessionTimeoutReplyTimeoutMs` | `number` | `undefined` | 用于保护窗口的回合超时长度的覆盖值；缺省时回落 `config.replyTimeoutMs ?? 600_000` |

**合并规则**（host config 与运行时 store）：

```
enabled         = hostConfig.sessionTimeoutEnabled === false ? false : store.enabled
timeoutMinutes  = store.timeoutMinutes ?? hostConfig.sessionTimeoutMinutes ?? 30
cleanupScope    = store.cleanupScope ?? hostConfig.sessionTimeoutCleanupScope ?? 'none'
其余字段         = store 字段 ?? 默认值
```

即：host config 显式 `false` 为最终否决；其它字段 store 优先于 host 默认。Host 启动时若两者不一致，会把合并后的默认值写回 store 持久化。这样既允许 cordis.yml 一刀切禁用，又允许用户通过 RPC 在运行期调整。

### 2.3 `workspaces.json`

**作用**：持久化各 bot/会话的目录隔离记录。本功能完整档清理时需要修改它的 `sessionDirectories` 子段。会话超时本身**不持久化到 `workspaces.json`**；本功能对它的修改仅是在配置为 `'directory'` 档时，删除既有 `sessionDirectories[botId][conversationKey]` 条目。

**位置**：`~/.dsh/integrations/dsh-<渠道>/workspaces.json`（每渠道一份）。无需手动编辑。

## 三、开启方式

按"先改配置 → 重启 → 用 RPC 微调"的次序操作。

### 3.1 方法 A：编辑 settings.json（推荐用于全新部署）

1. 停止 DSH Host。
2. 编辑 `~/.dsh/integrations/dsh-im/settings.json`，新增 `sessionTimeout` 子对象：

   ```json
   {
     "version": 1,
     "inboundAttachmentTtlHours": 168,
     "sessionTimeout": {
       "enabled": true,
       "timeoutMinutes": 30,
       "cleanupScope": "none",
       "notify": true
     }
   }
   ```

3. 启动 DSH Host。插件在启动时读取该文件并启动扫描定时器。

### 3.2 方法 B：cordis.yml 启动期默认（推荐用于 cordis.yml 部署）

1. 在 cordis.yml 的 `config` 段加上前述字段（§2.2 示例）。
2. 重启 DSH Host。插件启动期合并 host 配置与 store，并把合并结果回写 `settings.json`。
3. 之后用户在设置页（或 RPC）调整，store 字段会覆盖 host 默认；下一次 Host 重启会被 host config 重置为开启。

### 3.3 方法 C：运行时 RPC 微调（无需重启）

`/dsh-im-settings` 通道下提供三个 loopback 权限的 endpoints，可在 Host 运行时调整：

| endpoint | 入参 | 返回 | 含义 |
| --- | --- | --- | --- |
| `settings.session-timeout.get` | `{}` | 当前 settings 快照 | 查询当前配置 |
| `settings.session-timeout.set` | 任意 settings 字段子集 | 合并后的 settings | 原子写盘并重排扫描周期 |
| `settings.session-timeout.expire-now` | `{}` 全部 / `{"conversationKey": "<key>"}` / `{"conversationKeys": ["k1","k2"]}` | `{ expired: [...] }` 或 `{ ... summary }` | 手动触发清理，便于运维与测试 |

`set` 成功后会自动调 `service.resetSchedule()`；若从 disabled 切到 enabled 会自动启动扫描定时器；反向会停止。`expire-now` 的 `force=true` 会跳过 `enabled` 校验，**即使功能未启用**也能强制清理。

设置页（client 侧）后续会补对应的配置 UI，目前可通过 RPC 直接调用。

## 四、文件清理档位（`cleanupScope`）

文件清理是**与清理上下文正交、可选**的附加动作。即使 `cleanupScope='none'`，超时后仍会解绑 `conversationKey → sessionId`，下一条消息仍会开新 Session。

| 值 | 行为 | 安全保证 |
| --- | --- | --- |
| `none`（默认） | 仅解绑上下文，不动任何文件 | 最保守，与现状完全一致 |
| `inbound` | 复用 `sweepInboundAttachments(workspace, 0, { isTracked: () => false })`，以 TTL=0 强制清空记录目录（以及开启会话目录隔离时该对话目录内）的 `inbound/` 子树 | 仅清入站附件目录，不动其他文件 |
| `directory` | `inbound` 档基础上进一步删除整个 `conv-<...>` 目录，并从 `workspaces.json` 中移除对应 `sessionDirectories` 条目 | **必须通过四级安全校验**，任一失败自动降级到 `inbound` 档（详见 §五） |

### 4.1 `inbound` 档（推荐用于启用了会话目录隔离的部署）

清理流程：

1. 通过 `BotWorkspaceStore.sessionDirectoryFor(botId, conversationKey)` 取记录的 `directory`；若无记录则取 `defaultWorkspace` 作 base。
2. 对 base 调 `sweepInboundAttachments(base, 0, { isTracked: () => false })`——以 TTL=0 语义强制删除 base 下整个 `.dsh-im/inbound/<时间戳-随机>/` 子树。
3. 若记录的 `directory` 与 base 不同（即开启会话目录隔离），对 `directory` 也跑一次相同的 sweep。

清理失败不阻断解绑；清理后该 workspace 下无 inbound 目录时，`inbound-ttl-service` 后续 sweep 自然无操作。

### 4.2 `directory` 档（完整档，谨慎使用）

清理流程：

1. 取 `sessionDirectoryFor(botId, conversationKey)?.directory`；若无记录则**降级到 `inbound` 档**。
2. **四级安全校验**（任一失败即降级并记警告，绝不删除）：
   - **is-base 检查**：`directory === defaultWorkspace || realpathSync(directory) === realpathSync(base)` 为真时降级，**绝不删除 base workspace 根目录**。
   - **path-shape 检查**：`isConversationDirectoryPath(directory, { prefix })` 为 false 时降级，避免误删手动放入的同名目录。
   - **realpath 检查**：`realpathSync(directory)` 失败（ENOENT 等）时降级。
   - **outside-base 检查**：用 `node:path.relative(base, directory)` 计算，结果以 `..` 开头或为绝对路径时降级。
3. `rm(canonicalDirectory, { recursive: true, force: true })`。
4. 磁盘删除成功后调 `BotWorkspaceStore.clearSessionDirectory(botId, conversationKey, { alsoClearWorkspaceOverride: false })`，从 `workspaces.json` 中移除对应 `sessionDirectories` 条目。
5. 写盘失败**不回滚**磁盘已删目录，记「directory gone, record still present」状态，下次扫描二次清理并告警。

## 五、超时判定模型

### 5.1 触发点

每条 IM 消息进入与每个 agent 回合结束都会调 `service.touch(conversationKey, { botId, sessionId, at })` 重置该对话的空闲窗口：

- **入站消息处理**：fileIngress executor 在 stage 之前 fire-and-forget 调 `touchBySessionId(sessionId)`，重置活动时间戳。
- **agent turn 结束**：`session-sync-coordinator.mjs` 的 `processEvent` 处理 `turn/end` 事件时，也 fire-and-forget 调一次 touch，让"空闲"从回复完成算起。

两处都用「fire-and-forget + try/catch」：touch 失败只记日志，不影响消息收发。

### 5.2 扫描周期

固定间隔（默认 5 分钟，可配）跑一次 `scanAndExpire`，遍历内存活动表中所有 conversationKey，对 `now - lastActivityAt > timeoutMinutes * 60000` 者执行 `expire()`。扫描不读盘、也不写盘（仅当有条目被清理时才会间接影响后续状态）。

### 5.3 保护窗口（避免误杀长回合）

每个 tracked record 还可以记录 `runningSince`（最近一次 agent turn 开始时间）。扫描时若 `now - runningSince < replyTimeoutMs * 1.5`（默认 10 分钟 × 1.5 = 15 分钟），**跳过本次过期**，避免在长回合执行期间误判。超过保护上限仍未结束则正常过期。

### 5.4 首轮扫描 grace

活动记录只存在内存里，因此进程重启后所有对话都从「未跟踪」开始，空闲窗口重新计时——一个离线八小时的用户回来后，会先享有一个完整的阈值周期才被清理，而不是重启即解绑。

在此基础上仍保留一条 grace：首次扫描时，对已超阈值但 `age < thresholdMs + scanIntervalMs` 的条目放一马，给一个扫描间隔的宽限期，避免条目恰好在两次扫描之间 ageing 越线、又被（重）排期后的首轮扫描立刻清理。

### 5.5 通知文案（`notify=true` 时）

`expire()` 在解绑前调 `deliveryService.sendSessionSyncText(botId, targetId, sessionId, text)` 给该 Session 注册过的所有 sync target 发提示文案。

- 文案默认「会话超时，已开启新会话；如需继续上一段，请使用 /history」，走 dsh-im 既有的 i18n 字典，**不硬编码**；英文译为 "Session timed out; a new conversation has started. Use /history to continue the previous one."。
- 单个 target 发送失败只记日志，**不阻断其他 target 发送与解绑动作**。
- 如果该 Session 没有任何注册过的 sync target（普通飞书私聊通常属于这种情况），会通过 `conversationKey` 回退到渠道的主动消息发送入口；回退失败只记日志，不阻断解绑。

## 六、与既有机制的关系

| 既有机制 | 关系 |
| --- | --- |
| `inboundAttachmentTtlHours` / `inbound-ttl-service` | 与本功能**正交**。会话超时清理是一次性即时动作；长期附件淘汰仍由 `inbound-ttl-service` 周期 sweep 负责。两者不相互取消；会话超时清理后该 workspace 下无 inbound 目录时 inbound sweep 自然无操作 |
| `replyTimeoutMs`（单回合 10 分钟超时） | **仍然有效**。本功能不接管或替换它；仍在 running 的 agent turn 由它兜底；本功能的保护窗口 `replyTimeoutMs * 1.5` 也以它为基础 |
| `/new` 命令的解绑 | `/new` 走的是同一个 `ConversationStateStore.clearSession(key)`，**与本功能等价**；本功能只是把它自动化了 |
| `/history` 命令 | 本功能不动 Session 日志；`/history` 仍可找回旧 Session 继续对话 |
| 会话目录隔离（`conversationDirectory`） | `'directory'` 档清理复用 `sessionDirectoryFor`、`isConversationDirectoryPath`、`BotWorkspaceStore.clearSessionDirectory` 等；任一校验失败降级而非删除 |
| `/dsh-im-settings` | inbound TTL 与 session timeout 共用同一个 fetch route，由 method 前缀分别分发 `settings.inbound-ttl.*` 与 `settings.session-timeout.*` |

## 七、关闭与回滚

把 `enabled` 改回 `false`（或删 `sessionTimeout` 子对象）即可。关闭后：

- 不再扫描、不再解绑、不再清理文件；
- 已经被解绑的对话不会"绑回去"——下次用户发消息时会自动开新 Session；
- 已经被清理的文件不会恢复——这是有意识的清理动作。

如果只是临时调试，**推荐用 RPC `set enabled=false`** 而非删文件：删文件会让下一次启动按 host 配置 / 默认值重新初始化。

## 九、验收对照

- 默认配置下（`enabled: false`）行为与现状完全一致，无回归。
- 开启后，空闲超过阈值的会话在下一个扫描周期被解绑 `conversationKey→sessionId`。
- **核心**：解绑后下一条 IM 消息进入时 `sessionFor(key)` 为空，自动走 `createSession` 产生新 sessionId，用户在全新上下文中继续会话。
- `notify=true` 时，绑定的 IM 渠道收到「会话超时，已开启新会话；如需继续上一段，请使用 /history」消息。
- `cleanupScope='inbound'` 档清理后，`<workspace>/.dsh-im/inbound/` 下对应子目录消失，`inbound-ttl-service` 后续 sweep 不报错。
- `cleanupScope='directory'` 档清理后，`conv-*` 目录被删除，`workspaces.json` 中对应 `sessionDirectories` 条目被移除，且**不误删 base workspace 根目录**。
- 长回合执行期间不会被误判超时（保护窗口测试）。
- 活动记录不出现在 `settings.json` 中；重启后各对话的空闲窗口重新计时（内存态测试）。
- 已超时但仍在 grace 内的会话不被首轮扫描立即清理（grace 测试）。
- 单个 target 通知失败不阻断其他 target 通知与上下文解绑。
- `session-timeout.get/set/expire-now` RPC 工作正常，设置变更后扫描周期正确重排。
- **不销毁旧 Session**：超时前后旧 sessionId 的持久化日志仍在磁盘上，`/history` 可访问。
